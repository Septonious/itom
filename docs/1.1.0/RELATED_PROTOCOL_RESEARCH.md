# Related transport research — 20 October 2026

Purpose: borrow testable design ideas for IMAP, not transplant an unrelated wire protocol or accept author benchmarks as ITOM evidence. No third-party code was copied into final1.0.0 or the initial timing prototypes.

Tune each direction independently; measure amplification and queue residence. Dropping locally is recoverable only where the reliable layer knows ownership: ITOM must not drop an unknown physical APPEND or erase charges. |

## Experiments derived from this review

1. Immediate tiny-write dispatch versus RC2 coalescing: measure saved wait plus extra MIME/record/fsync rate, including small TLS writes during bulk.
2. Demand-scoped polling scaled by measured provider command RTT: measure empty commands, socket churn, CPU and tails. Keep idle notification mode and normal bulk policy unchanged.
3. Completion-time account scheduling with bounded exploration/hysteresis, trained separately for APPEND, visibility and BODY. Never train physical capacity from logical RTT alone.
4. Joint polling/control/data budget with latency priority and bounded fairness. Cleanup/recovery remains serviceable; lower mean RTT cannot hide p99 stalls or download tails.
5. Direction-specific window/pacing from authenticated useful bytes and feedback age; test against RC2 unchanged bulk sizes/windows before combining changes.

Numbers from these projects' own throughput comparisons are not reproduced here: different carriers, hardware and workloads cannot establish an ITOM improvement. Current local experiments use actual ITOM supervisors/TLS/IMAP/fsync, not a generic mathematical simulator, and still need real-provider validation.
