# FIELD44 — состояние кандидата и проверки

Дата: 7 октября 2026. Ревизия: `transport-s1-perf5-field23`.

## Назначение

Экспериментальный релиз для локальной и полевой проверки пользователя. Пользователь запросил частые кандидаты с точечными проверками вместо полного повторного тестирования. Мобильная приёмка ещё не пройдена; пороги проверки не снижались. FIELD42 FIX1 остаётся ранее сохранённой рабочей базой подключения. FIELD43 — предыдущий UI-кандидат.

## Изменения относительно FIELD43

- Начат общий контроллер под `stripeGroup.mu`: один бюджет скорости вместо второй очереди будущих APPEND; обратная связь по RTT и BODY использует общий допуск отправки.
- Скорость ниже 9,5 Мбит/с не снимает защиту при высоком или устаревшем RTT. Внутренний минимальный темп проб 1 Мбит/с не является новым порогом приёмки.
- Класс job фиксируется владельцем TCP-потока и согласован между Pump, grants и физическим writer. Накопившиеся мелкие фрагменты длительного потока считаются bulk.
- Исправлено срезание накопленного бюджета большим batch при опросах меньших batch.
- FIELD44 добавляет общий предел непрочитанных download BODY. Учитываются все прикреплённые аккаунты и ожидающие APPEND, чтобы параллельные writers не использовали один свободный остаток несколько раз.
- Начальное окно — 1 МиБ; затем окно зависит от фактически подтверждённой скорости и текущего RTT-ограничения. Верхний предел — 4 МиБ, нижний — два наиболее крупных наблюдавшихся batch. Это advisory-лимит полезных байтов, не изменение протокольного WINDOW или квот IMAP.
- В window-wait не удерживается физический APPEND-слот. При отмене до APPEND prepared journal attempt отменяется по существующим правилам. После регистрации outgoing pending-резерв снимается; early/partial/duplicate receipts корректно отражаются в непрочитанном объёме.
- Batch с аутентифицированным DATA repair имеет отдельный единственный pending-допуск вне окна новых данных, чтобы потерянный BODY не блокировал своё восстановление. Ограничения скорости, физического параллелизма и долгов продолжают действовать. Этот допуск сам по себе не создаёт повторную отправку.
- Добавлены диагностические поля `DownloadWindowBytes`, `DownloadBacklogBytes`, `DownloadPendingBytes` и русские подписи.
- UI FIELD43, исправления truncated BODY/BINARY и закреплённый IMAP fork сохранены. Меняются ревизия CLI/trace/source-info и Android versionName/versionCode. `UI_BASELINE` остаётся прежним, поскольку дизайн этой ветки не перерабатывался.

## Выполненные точечные проверки

19 различных tunnel-тестов с race detector прошли: контроллер, token budget больших/малых batch, window/pending reservations, repair при заполненном окне, отмена prepared DATA без утечки квот и слотов, fast-slot во время ожидания bulk, partial/early receipts без возврата физических квот, единый снимок готовности. Некоторые проверки запускались до и после добавления только диагностических полей; точные результаты находятся в приложенных журналах.

Один тест реального native TCP-моста прошёл: 7 параллельных TCP-соединений, half-close отправки, целостность ответа, активная отмена. Это проверка моста, не квалификация IMAP-пропускной способности.

Linux amd64/arm64 cross-build прошёл; CLI amd64 выводит `ITOM transport-s1-perf5-field23 linux amd64`. Закреплённый манифест локального IMAP проверяется перед упаковкой. Полный Go suite, полный vet, Kotlin suite, Gradle lint и APK/AAR-сборки в этом релизе не повторялись. Android нужно собрать локально стандартной командой из README.

## Один короткий прогон модели

Модель HTTPS через IMAP: 10 аккаунтов, общий доступ 20 Мбит/с, дополнительный RTT 250 мс, без потерь на relay. Старое состояние 8 МиБ, потерянные старые публикации 3/10 аккаунтов. BINARY FETCH включён, APPEND остаётся base64. Трафик проходит настоящий TCP/TLS/HTTP и IMAP-тестовый сервер; модель не эмулирует радиосеть, TCP congestion в ядре или Rambler полностью.

| Показатель | Значение |
|---|---:|
| Режим | download, 15 секунд |
| Фактический замер | 15 023 мс |
| Средняя полезная загрузка | 2,007 Мбит/с |
| Последняя часть замера | 3,859 Мбит/с |
| Максимальный HTTP RTT | 1861 мс |
| Ошибка передачи приложения | нет (`failure=<nil>`) |
| Итог тестового gate | FAIL |

Результат НЕ подтверждает устранение зависаний и обрушения линий в поле. Средняя скорость низкая, RTT выше требуемого. Выгрузка, duplex, нестабильность/смена скорости канала, долгий прогон и быстрый канал не проверялись этой сборкой. Сравнение с прежними замерами разной длительности нельзя считать доказанным приростом.

После этого прогона изменены только диагностические поля, текстовые подписи, версии и дополнительные lifecycle-проверки. Основной механизм окна тот же, что в прогоне.

## Следующая итерация по полевым логам

Проверить, сопровождается ли деградация заполненным `DownloadBacklogBytes`, отсутствием свежих подтверждений BODY или нехваткой grants. Затем корректировать взаимодействие размера batch, окна и повторной передачи, сохраняя протокол и учёт неопределённых APPEND. Не объявлять мобильную стабильность по одному короткому прогону.
