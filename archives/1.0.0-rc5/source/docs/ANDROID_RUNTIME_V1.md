# Android runtime · android-3

## Владение и остановка

Один серверный процесс создаёт по lane на пару account/user. До handshake lane
использует одну IMAP-сессию. После аутентификации создаются ещё две: одна для
приёма, одна для APPEND; исходная обслуживает физический GC. При двух активных
пользователях это до шести серверных соединений на аккаунт и по три на каждом
телефоне — до двенадцати суммарно. Отказ дополнительного connect/login допускает
работу через две/одну уже защищённые TLS-сессии, с явным `event=io_mode` в журнале.
Ошибки TLS не запускают fallback. Снижение числа соединений уменьшает изоляцию I/O.
Статистика по-прежнему считает два направления папок логическими линиями,
а не показывает число внутренних сокетов. Приём и GC выполняются отдельными
задачами, меняет протокольное состояние только основной обработчик сессии.
Все аккаунты участвуют в распределении новых потоков; закреплённого разбиения 5/5 нет.
Сервис Android последовательно закрывает предыдущий native Client перед следующим,
а SessionMachine отвергает устаревшие callbacks. Конфигурация и секреты считываются
атомарно по revision из VaultStore. Intent содержит только идентификатор и revision.

Новый пользовательский поток получает odd stream ID. OPEN отправляется только
после Noise, activation и coordinator binding. Серверный TCPExit проверяет адреса,
запрещает private/loopback/link-local destinations, ограничивает параллельные dial.
Клиент возвращает socket только после OPEN_OK. Ранние WINDOW ограниченно буферизуются.
Pump владеет сокетами и буферами; RESET освобождает логические данные только своего
потока. Физический долг RESET не отменяет. IMAP write failure завершает всю lane.
После 4096 OPEN в одной эпохе lane перезапускается, сохраняя ограниченный размер
таблицы tombstones. Учитываются и отклонённые OPEN. Текущие TCP этой lane при такой
ротации закрываются; плавное осушение и возобновление TCP ещё не реализованы.

## Протокол и хранение

ITH4 — версия handshake envelope с binding, включающим server/user/account/folders.
ITC1 — одиночный аутентифицированный control frame; ITB1 — до 16 независимых
Noise control records в одном письме. Каждый record имеет собственный counter.
Пакет очищается только после подтверждения всех его non-receipt records. ITQ1 — клиентский DATA,
разрешённый серверным grant. Серверный DATA использует локальный журнал.
Внешний wire остаётся v2; новое управление MAIL_RECEIPT имеет type 6 и ограниченный
список counters этой Noise-сессии. Старый probe-сервис и android-1 с ITH4 несовместимы.

MAIL_RECEIPT подтверждает приём/владение кадром, но не является доказательством GC.
Отправитель делает полный FETCH, сверяет SHA-256 и UIDVALIDITY, удаляет именно это
сообщение, проверяет отсутствие и лишь затем освобождает физическую квоту. Сам receipt
не вызывает receipt. Новый полный snapshot заменяет предыдущий receipt и разрешает
его удаление; ещё нужные подтверждения сохраняются до проверки удаления сообщений.

На server/account/user выделены фиксированные DATA 8 MiB/128 сообщений и control
2 MiB/128 сообщений. Совокупный предел двух пользователей — DATA 16 MiB и control
4 MiB на аккаунт. Control не расходует DATA-бюджет. До шестнадцати активных клиентских grant
по 64 KiB/одному сообщению входят в тот же DATA-ledger, а не добавляются поверх него.
Grant Spend журналируется до APPEND, затем отправляются Usage/Release. После доказанного GC выдаётся замена grant без ожидания retirement; до64 grant
вместе с неубранными метаданными остаются жёстким пределом. GC_STATUS и retirement
завершают цикл; потерянные control-снимки повторяются из wallet.
Неизвестный APPEND без доказуемого UID остаётся занятой квотой даже после рестарта.
Смена эпохи не создаёт новый журнал. При перезапуске удаляются только сообщения,
доказанно принадлежащие старой, уже остановленной сессии.

## Android

VpnService перехватывает IPv4/IPv6; разрешены TCP/IPv4 и DNS, остальные UDP/IPv6
не передаются наружу. Provider и Direct сокеты вызывают VpnService.protect до connect.
Bootstrap DNS выбирается из текущей underlying network, исключая собственную VPN,
включая после смены Wi-Fi/мобильной сети. DNS mapping хранится в общей для профилей
приватной БД, чтобы переключение профиля не переназначало закешированный fake IP.
Domain rules применяются к имени из fake DNS/SOCKS; IP/CIDR rules — к входному
числовому адресу. IP, полученный сервером при разрешении имени, не возвращается
клиентскому Router для второго сопоставления. Внешний DoH/DoT не декодируется.
Native fd передаётся detachFd и закрывается единственным native владельцем.

Для foreground-service используется specialUse с описанием VPN use case;
SDK 34+ получает явный foreground type. Документация:
https://developer.android.com/develop/background-work/services/fgs/service-types
https://developer.android.com/develop/connectivity/vpn

Зависимости native закреплены в native/go.mod/go.sum. tun2socks v2.7.0 (MIT)
используется как библиотека TCP/IP, с собственным TransportHandler ITOM;
gVisor — Apache-2.0; Go/x packages — BSD-style; Noise/IMAP/journal pins сохранены.
Сборщик использует gomobile v0.0.0-20260908204917-8b95e45f8d3e и NDK 28.2.13676358.

## Оставшиеся проверки

Нужны локальная Android сборка/lint, запуск на устройстве, реальный профиль Rambler,
проверка web/скачиваний/двух пользователей и переключения сетей. Эта ревизия не
приписывает локальному IMAP тесту скорость или надёжность реального провайдера.
Долговременное восстановление, крупные transfer, смена UIDVALIDITY и провайдерские
лимиты требуют дальнейшей квалификации. Ускорение polling/batching/IDLE следует
выполнять по её данным, сохраняя контракт журналов и очистки.

## Сохранённые механизмы android-2

Control writer имеет обычную очередь до512 кадров и приоритетную до64; при
заполнении приоритетной доступен обычный резерв. Batching до16 и задержка сбора до
10 ms. WINDOW/RECEIPT одного stream внутри batch заменяются более свежим значением.
Полный MAIL_RECEIPT (до512 counters) имеет отдельный latest-only slot и проходит
даже при backpressure обычного control. Обычные control APPEND останавливаются
при80занятых control messages или320удерживаемых records; для ACK оставлен резерв.
Число records учитывается до физического GC, а не до логического ACK. DATA writer
ждёт свободную локальную квоту **до** claim/APPEND; неопределённый APPEND не повторяет.
Физические лимиты журналов не повышались. Первый control или DATA write error
передаётся owner через отдельный error channel и закрывает lane.

GC получает максимум32 сообщения в batch. Полный FETCH и hash сверяются для
каждого UID; STORE/EXPUNGE/повторный SELECT/проверка отсутствия объединены. Ошибка
в середине оставляет долг для recovery. Remote DATA сначала сохраняется в Pump,
потом очищается отдельной фоновой задачей по неизменяемому снимку. GC_STATUS и retirement отправляются
сразу; периодический5s обход wallet — только повторная доставка, не путь кредита.
Именно ожидание periodic retirement в раннем промежуточном тесте ухудшало скорость;
оно исправлено до выдачи этой версии.

Сервер запоминает UID/UIDVALIDITY принятого hello. Старые hello с меньшим UID не
могут заместить текущую сессию. Ожидание клиента не ограничено90s на сервере;
каждая IMAP-операция по-прежнему имеет30s предел, отмена службы прерывает ожидание.
Повторная авторизация использует экспоненциальную задержку с jitter, чтобы линии
не переподключались одновременно. Gate/OPEN retries8s, DATA probes5s. Bootstrap сохраняет собственную policy,
но его deadline теперь начинается после activation, а не одновременно с ней.
Все пользовательские данные и ограничения UDP/IPv6/IP routing остаются как выше.

## Изменения android-3

Актуальная схема I/O, fair scheduling, bounded coalescing, результаты и ограничения
описаны в `TRANSPORT_ANDROID3.md`. Физические лимиты DATA/control не увеличены.
