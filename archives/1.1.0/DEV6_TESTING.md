# ITOM 1.1.0 DEV6 — experimental testing RC

DEV6 fixes a reproduced reason for **24/30 lines** on DEV5: three accounts have established IMAP sockets but cannot obtain both fast and bulk grants because historical reservations exhaust fixed quota cushions. The new allocator adjusts only the fast cushion to genuinely free directional headroom, keeps full-size bulk BODY capacity in both directions and preserves every old charge. Fast refills no longer double-reserve an existing bulk allowance. Fallback DATA also repairs a known-dead control socket before APPEND without replaying uncertain publications.

Use the DEV6 server and app together. **Update the APK in place and keep the existing server state directory.** The APK keeps `org.itom.client`, increases versionCode from DEV5's 10105 to **10106**, and uses the same persistent signing certificate as the public DEV5 APK. Preserve app wallet data and server journals; a clean install cannot prove that old reservations were unused. Historical debt too large to leave the complete duplex minimum still blocks safely. DEV6 neither erases old debt nor promises to revive every exhausted account.

The new real TLS/IMAP regression reaches **30/30 directions** and verifies short/bulk/short exchanges on every one of fifteen accounts under retained byte pressure. The same three field-shaped allocation cases fail on frozen DEV5 and pass on DEV6. Normal profiles keep their existing fast/bulk sizes. Diagnostics expose historical charges, actual free headroom, the chosen fast reserve and missing-wallet audit counts.

**Matched laboratory results:** DEV6 19/20 sustained rounds versus RC2 19/20; DEV6 48/48 short phases versus RC2 42/48. Against DEV5 both variants pass 36/36 short phases, with measured mean bandwidth changes from −2.7% to +5.7% across three fixtures. The worst raw-4G test delivers 0.287 Mbps in each direction, 66 exchanges, zero failures. Server network latency is modeled at **20 ms**. These are simulated-provider results, not Rambler field measurements. Rates above 200 Mbps in the lab do not predict phone/provider throughput.

**Known failures remain.** One sustained mobile tail is 99.457 Mbps, below the unchanged 100 Mbps gate. The race-enabled mixed-load test still misses its original 1100 ms chat deadline; the miss also reproduces on unchanged DEV5. A separate capped-socket stress run under CPU contention fails 6/30 repetitions, despite isolated 20/20. Every failed observation is retained. The testing APK is built with an explicit exception for that known loaded-race timing diagnostic; this is **not an all-checks-passed or fully qualified release**. No data race or accounting failure is permitted by that exception.

The production changes improve reproduced quota-bound readiness. **Lower real-world idle RTT, reliable completion of all field Speedtests and elimination of every stall are not established.** Test startup first, then repeat SINGLE and MULTI runs without clearing app/server state. The export can now distinguish socket readiness from quota starvation.
