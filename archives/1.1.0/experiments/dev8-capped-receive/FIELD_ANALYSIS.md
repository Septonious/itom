# DEV7 field feedback: control receive and short-start regressions

The supplied client is `1.1.0-dev7-debug`. It reports 30/30 active lines and zero carrier reconnects. The successful SINGLE screenshot reports 23.3/71.2 Mbps, 416 ms idle RTT, 758/911 ms loaded RTT, and 172 ms jitter. Three additional Speedtests failed according to the user.

The rotating client trace covers approximately 12:18:45–12:21:16 UTC on 23 October; the server trace starts later, around 12:19:23 UTC. These windows do not cover complete startup or identify all four application test boundaries. The retained client has 186 OPEN_OK records. Socket failure events describe application streams; they are not evidence of lost IMAP account connections. This capture therefore cannot, by itself, prove the cause of every reported Speedtest failure.

The physical roles are two client sockets (control and DATA receive) and three server sockets (control, DATA receive, and shared DATA writer). Control receive, APPEND, and physical cleanup contend for the control connection. The server retains approximately 8.6–11.2 MB and 140–173 message slots of historical DATA reservations per account. The client also reports dozens of missing-wallet recovery offers per account. This debt remains charged: timing, old age, missing wallet history, and successful synthetic tests do not authorize a refund.

A concrete scheduling fault exists in that layout: the live control reader acquired the account maintenance class, including its single maintenance slot. It could wait behind unrelated maintenance even when its own control socket was free. DEV8 gives live reads the existing receive class while retaining fair serialization on the actual shared socket. Inventory and destructive proof work retain maintenance admission. A deterministic TLS mailbox regression fails on DEV7 with a read deadline and succeeds after this change.

The first capacity fixture used one old grant per account. It has been extended to optionally distribute the same exact byte/message charge over 48 old grants per account. This adds reconciliation traffic without inventing spent bytes or zero-spend fences. Endpoint budgets are now independently configurable: account_sessions=5 meant two sockets on each endpoint, not the previously assumed three server/two phone sockets. The new field case uses a six-session server configuration and four-session imported phone profile, which produce those separate endpoint limits. Actual socket roles are logged rather than inferred from mailbox counts.

The new application regression exercises fresh TLS/HTTP starts, single/four-flow ramps, partial downloads aborted by the application, and a persistent 32-byte light-request connection before and after each ramp. The existing 750 ms light-request and 1500 ms OPEN deadlines remain unchanged. Provider path propagation remains independently configured, with a default 20 ms server path and a separate variable 40–180 ms phone sensitivity case.

An idle-test reporting error is also corrected: after a request timeout, the old fixture compared the late reply with the next request on the same byte stream and reported cascading corruption. The timeout remains a test failure; later measurements use a new stream. Earlier logs with that cascade must not be counted as independent corruption failures or used for aggregate successful-request latency.

A second deterministic defect affects bounded UID discovery after concurrent cleanup. The cached SELECT allocation snapshot can be behind an entire expunged scan window. A new short response beyond that window is then invisible to the bounded FETCH until the two-second audit. Six TLS-mailbox cases reproduce this on DEV7, with one-, four-, and sixteen-UID pages, both with and without IDLE consuming the notification first.

DEV8 retains an independent new-mail discovery hint. After an empty scan that cannot reach beyond the cached allocation horizon, a bounded UID SEARCH locates candidates. Only a fresh tagged-successful SELECT with unchanged UIDVALIDITY permits candidate BODY delivery. SEARCH and EXISTS cannot refund quota or independently advance the cursor. Known allocation holes use the actual requested page limit rather than a fixed sixteen-UID threshold. All six new cases and the existing selection/sparse/discovery tests pass locally; dense pages retain their existing command behavior.

Two experiments were rejected before packaging: faster polling on shared split control and earlier FAST proof scheduling. Their repeated application results were inconsistent. Neither is present in the selected production source. Qualification of the selected receive/discovery fixes is pending. Synthetic bandwidth and application timing are not predictions of real Rambler or Android performance.
