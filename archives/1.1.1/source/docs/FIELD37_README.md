# ITOM FIELD37 — запуск четырёх аккаунтов Mail.ru

Ревизия `transport-s1-perf5-field16`, исходники `ITOM_TRANSPORT_FIELD37_SOURCE.zip`.

Новые реальные логи отличаются от предыдущего случая с VPS: сервер FIELD15 успешно входит в четыре аккаунта Mail.ru и публикует challenge; Android FIELD14 во всех трёх попытках получает `IMAP_CONNECT_FAILED` через 20 секунд, до TLS/LOGIN. Сервер отдельно переподключается при ожидании клиента примерно через 16 секунд. Точный нижележащий DNS/TCP отказ клиента и причина серверного закрытия старой трассировкой не установлены. Rambler исключён из текущего сценария проверки; существующие пользовательские аккаунты и профили автоматически не удаляются.

Исправлены слабые места Android-сети: DNS через `Network.getAllByName` выбранной исходной сети вместо UDP-запросов только к первому DNS; protected TCP сокеты привязаны к этой сети до connect. IPv4/IPv6 подключаются с ограниченной параллельной попыткой второго семейства, отменой проигравшей попытки и закрытием лишнего сокета. TCP4 и IP-literal поддерживаются; проверка TLS использует исходное имя провайдера, IP не подставляется в конфигурацию.

Ожидание pre-auth использует IDLE/DONE на базовом сокете до выделения независимых работников; без IDLE — bounded polling раз в 500ms. SELECT проверяет UIDVALIDITY раз в 2s, FETCH остаётся ограничен 16 UID, восстановление журналов не меняется. Настоящие SELECT/FETCH теперь видны в диагностике до активации. Ошибки операций получают безопасную категорию `reason`; IMAP decoder сохраняет тип ошибки закрытого сокета.

Это кандидат для проверки восстановления соединения на устройстве. Работоспособность реального Mail.ru и скорость >=75Mbps не подтверждены локальными тестами. Сборка APK, Android lint и устройство должны быть проверены target `all` на машине пользователя; обновить нужно именно APK, поскольку главный сетевой дефект находится на клиентской стороне. Сервер обновить для снижения pre-auth трафика и новой диагностики. Wire/capabilities совместимы с FIELD14/FIELD15, однако смешивание ревизий не проверяет новый Android путь.

Сборка Windows PowerShell:

```powershell
python .\ITOM_TRANSPORT_FIELD37_SOURCE.zip all --expect-revision transport-s1-perf5-field16 --accept-android-licenses
```

Обновление VPS amd64 после копирования бинарника в `/tmp`:

```bash
chmod 755 /tmp/itom-linux-amd64 && sudo /tmp/itom-linux-amd64 install
```

Результаты: `docs/FIELD37_RESULTS.md`. `sudo itom imap-check --account a01` остаётся read-only проверкой TLS/LOGIN/NOOP одного аккаунта. При повторном отказе нужны новые архивы обеих сторон FIELD16: connect `stage`/`reason`, затем `imap_error reason`, чтобы различить DNS, TCP, protection, TLS, LOGIN и закрытие после входа. Исторические замеры FIELD35 и предыдущие результаты сохранены в docs; они не являются доказательством работы нынешней реальной сети.
