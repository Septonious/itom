# ITOM 0.9.2 Rev11 — targeted transport recovery handoff

## Candidate and qualification scope

Rev11 targets the repeated receive reconnection churn observed when attempting Speedtest on Rev10. It preserves a working IMAP connection through a bounded temporary silence, retains a finite repair deadline for genuine blackholes, and keeps the original logical TCP session and durable accounting. The exact final selected checks and Android build results are in VALIDATION.json and TEST_EVIDENCE.zip. This is a targeted testing prerelease, not a complete stable certification. The full final internal suite, physical Android phone, live Rambler Speedtest, strict 100 Mbps and jitter qualification have not been rerun. No new throughput number is claimed from the finite integrity ramp regression.

## Field evidence and causal limits

The new client and both server captures identify 0.9.2 Rev10. Matching authenticated frame session/counter identities confirms ordinary transit-scale timing between endpoints; there is no multi-minute clock displacement. The client capture covers 18:42:44–18:46:19 UTC. The two server exports stop at 18:43:27 and 18:44:29, before the largest client failure wave at 18:45:36 UTC (21:45:36 Moscow time), so they do not establish server behavior during that wave.

The client reports simultaneous read EOFs across physical roles, briefly restores DATA writers, then records seven DATA receive command timeouts at almost exactly 1500 ms. Preserved mixed-receive socket generations also show `receive / no_progress` at 1500 ms. Resets and another DATA-capacity oscillation follow. The server independently records two 1500 ms DATA receive timeouts before its export ends. The client session_stop at 18:46:19 UTC is intentional cancellation and is excluded from the transport-failure diagnosis. Capability callbacks do not record an underlying-network selection change alongside the broad EOF event.

The first external EOF cause remains unconfirmed. The concrete defect addressed here is an amplifier: a 1.5-second no-read watchdog, calibrated from unloaded IMAP NOOP latency, closes otherwise live connections through a short congestion/retransmission pause. Re-selection and replacement LOGIN then add work during the impaired interval. A local TLS/IMAP fault injection reproduces that premature close without closing the server socket or changing credentials. Raw user captures remain private; no credentials or provider message bodies are published.

## Runtime changes and bounds

`core/mailbox/receive_interrupt.go` defines a shared eight-second receive-progress floor and ten-second ceiling. The floor permits a short consecutive TCP recovery interval instead of treating fast unloaded NOOP latency as a worst-case bound on a busy path. Both the tunnel guard and the IMAP DONE-completion watchdog use this policy. The guard measures absence of actual socket read progress; successful reads still extend it. Local callback backpressure remains excluded as before. The separate absolute command cap remains thirty seconds, and application/liveness timeouts are not silently replaced by this receive guard.

`core/tunnel/receive_worker.go` uses the same floor, with the existing bounded extension from independently sampled provider RTT. This does not delay normal FETCH, authenticated packet processing, local wake signals, IDLE notifications or empty-tail audit cadence. It changes when a silent physical receive socket is destroyed, not when available data is delivered. EOF, reset and explicit cancellation still end failed physical generations promptly; a genuine silent blackhole remains bounded rather than waiting indefinitely.

`core/tunnel/topology.go`, `io.go` and `mail_socket_diagnostics.go` retain one previous failed DATA receive generation, including its first-close stage/reason. Earlier snapshots retained control/mixed-reader history but lost the DATA receiver cause as soon as the pointer was replaced. This is diagnostic state only: no UID cursor, message digest, mailbox locator, quota refund or delivery proof is inferred from it.

Rev10 bounded control-replacement retries and immediate minimum DATA writer restoration remain active. Rev9 IP pinning, verified TLS hostname identity, protected Android socket routing, persistent IMAP connections/keepalive and independent admin rollback remain intact. No crypto identity, authenticated counter, carrier epoch, allocation debt, journal, GC proof, resource limit or provider account is reset. No uncertain APPEND is replayed to accelerate recovery.

## Targeted regressions

`core/tunnel/rev11_receive_stall_test.go` extends the production supervisor fixture. The provider fault pauses TLS response bytes on the existing client sockets without closing them. It targets the client endpoint connections explicitly; server-side IMAP connections are not included accidentally.

1. Ten accounts, retained durable allocations and twenty logical lines: a 2400 ms pause across fifty existing client sockets must preserve all twenty original physical receive sockets, the original application TCP connection, and a fresh verified 256 KiB transfer. The original code fails with `receive / no_progress`. The revised code must retain the generations and report zero receive reconnects.
2. Ten accounts and twelve concurrently ramping TCP streams: each transfers and verifies one MiB in each direction through the same 2400 ms pause. The original messaging connection, all twenty receive sockets and all twenty logical lines must remain usable; a fresh transfer and another original-socket exchange after a quiet interval must pass. This is an integrity/recovery regression, not a sustained throughput measurement. Race instrumentation has a separately declared application-transfer completion allowance and is never used as a performance certificate.
3. A persistent twenty-second provider-response blackhole must retire the silent receive generations within the existing bounded test deadline, preserve the logical carrier, retain the DATA receiver first-close diagnosis, and permit the original application TCP connection to recover after the injected outage is released. The fault's old control generation is closed explicitly when releasing the fault; uncertain APPEND ownership remains conservative.

The selected race run also retains Rev10 discovery/all-client-socket-loss recovery and transient-control retry boundary checks, plus the existing mobile receive-policy test. A separate normal run includes the new tests, Rev10 simultaneous socket loss, Rev7 post-bulk correlated control EOF recovery and capped mixed-socket recovery. Selected source/build launcher checks verify the new revision identity. The build also requires native host tests, Android domain/app unit tests and lint. Exact logs, test membership, durations and candidate fingerprint are bundled; targeted checks do not imply a complete matrix pass.
