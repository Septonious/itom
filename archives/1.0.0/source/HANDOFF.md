# ITOM 1.0.0 RC1 — stabilization handoff

## Current status

This is the 1.0.0 release candidate containing the MULTI missing-range recovery correction and checkpointed receive-stall recovery work. It is a testing prerelease. The exact final targeted test/build results are in VALIDATION.json and TEST_EVIDENCE.zip. The complete final internal matrix, live provider/physical Android run, sustained strict 100 Mbps duplex and jitter qualification are not claimed. The user's requirement that all internal gates pass before a stable release remains in force; reduced targeted validation does not silently become full stable qualification.

## Field findings

The user moved back to the old server and reports the broad disconnect problem resolved. The new captures identify Rev10 and end with twenty client lines connected. The supplied SINGLE screenshot reports 101 Mbps download, 77.9 Mbps upload, idle ping 302 ms and jitter 73 ms. This is useful real-provider evidence, not a sustained 100/100 certificate. Raw captures remain private.

Residual MULTI errors occur at the application-stream layer while physical lines remain connected. A captured stream has a 32 KiB receive gap while later DATA offsets arrive, an authenticated NACK, and application cancellation before the next repair cycle completes. The engine discarded NACKs while a physical writer still owned the original attempt or while the existing 1750 ms bulk BODY visibility grace was active. That can add another periodic probe cycle to ordered delivery. Most target connection attempts in the retained server trace succeed; an application reset alone does not prove that the mailbox lanes failed.

380 complete field echo exchanges have median RTT about 342 ms, p95 about 681 ms and maximum about 1401 ms. Median local control-queue wait is about 1.4 ms and p95 about 45 ms. Some long delays are visible while waiting for an IMAP read/SELECT to complete. These are sampled end-to-end control RTTs, not a jitter guarantee, and isolated one-way timing is not certified from unrelated clocks. Removing the repair delay addresses an avoidable head-of-line stall; it cannot establish a hard provider jitter bound.

## Core repair correction

`core/datapath/engine.go` retains at most one authenticated deferred NACK intent per pending logical item. It records only the overlapping peer-requested byte interval and its request ID. It does not consume a repair permit or start another physical write while the original still owns the writer or while BODY visibility grace remains active. Once the existing gates end, Poll activates the retained intent without waiting for a second peer request. Receipt/pruning and existing repair ID/retry limits still apply. Definite NotCommitted originals remain ordinary queued originals, rather than becoming extra repair copies. A receipt may cancel repair intent but never refunds physical debt.

The existing physical repair operation republishes the same immutable item when a valid overlapping missing range authorizes it; partial-range repair metadata was not redefined in this change. The retained authorization is intersected with the current item's range. Noise counters, identity, original byte content, grant charging and deletion proof remain authoritative. No uncertain MIME body is blindly replayed and no journal debt is reset.

`core/datapath/pump.go` clears an obsolete scheduling wake exactly once when a retained authenticated repair becomes eligible. Such a wake may depend on the ACK blocked by the missing range itself. The physical adapter still checks visibility, available grant/flight/repair slots and quota. A failed physical admission can park again on its newly returned wake; this is not an unrestricted retry loop.

## Receive recovery and diagnostic history

The checkpointed Rev11 work is included. A live socket pause of 2400 ms previously triggered the 1500 ms no-read watchdog, generating replacement LOGIN traffic through the same impairment. A common eight-second receive recovery floor with ten-second ceiling now covers the tunnel guard and IMAP DONE completion. Provider RTT may extend that floor within the bound. The thirty-second absolute command deadline remains separate. Normal available DATA, IDLE notifications, local wakes and audit cadence are unchanged; EOF/reset/cancellation still terminate failed generations promptly.

One previous DATA receiver snapshot retains first-close stage and reason after physical replacement. This matches existing control/mixed-reader history and adds no cursor or quota authority. The old no-progress test is updated to inject a genuinely persistent stall beyond the new floor; a three-second stall is now explicitly expected to survive instead of causing repair. Rev10 control retry priority and minimum DATA writer restoration, Rev9 verified-TLS IP pinning and persistent IMAP reuse remain active. The categorized server-admin UI and single diagnostics progress indicator are preserved.

## Validation and its limits

The focused early-NACK regression reproduces discarded requests in the original engine. New tests require deferred authorization to survive writer ownership and visibility grace, preserve the requested overlap and immutable bytes, avoid duplicate-ID amplification, keep definitively unpublished originals ordinary, and cancel on receipt without refunding physical debt. Retained repair/admission tests protect existing semantics.

The production-supervisor fault cases use real local TLS/IMAP sockets, ten accounts, retained durable allocations and twenty lines. A temporary response pause must preserve all twenty original receive sockets and the original application TCP stream. A twelve-stream ramp verifies twelve MiB in each direction through the pause, followed by a fresh transfer and an original-socket exchange after quiet. A true blackhole must trigger bounded receive repair. The ramp previously timed out with healthy receivers under race instrumentation; it completes with the retained-NACK correction. Exact source-bound logs and exploratory earlier failures are bundled separately and must not be represented as final passes.

The final selected race checks also cover transient-control retry boundaries, correlated client-role loss, receive policy and existing repair cases. A separate normal run covers ramp/pause, persistent blackhole, all-client-socket loss, post-bulk correlated-control EOF and capped mixed-socket recovery. Source/build launcher tests, native host checks, Android domain/app tests and lint are required by packaging. These are targeted checks, not the complete final internal suite or a physical device speed certification. An exploratory race run of the older capped mixed-socket case exceeded its fixed twelve-second transfer deadline; its normal rerun passed in about 2.7 seconds. That unresolved instrumented timeout is retained as a qualification limit and prevents claiming every internal gate passed.
