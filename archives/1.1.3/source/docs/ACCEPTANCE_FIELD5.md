## Мобильные условия

Ping100–300 ms, симметричная доступная клиентская wire bandwidth10–600 Mbps (особое внимание50–200), вероятность потери сегмента0–5%. Сервер/VPS link отдельно от клиентского mobile link. Физическое отключение аккаунта и network loss — различные события.

Go-модель ниже TLS: настоящие IMAP/TLS sockets, независимые очереди направлений, bounded buffering, сегменты1400 bytes, воспроизводимый seed, сохранение порядка и всех байтов, дополнительная задержка/байты при повторной передаче. Это reliable-stream impairment model, а не kernel TCP/netem; congestion control TCP и настоящие kernel packet drops этой моделью не проверены. Системный netem недоступен в данной среде (нет NET_ADMIN и возможности создать отдельный network namespace).

Временный NOOP baseline и client-only shaping привязаны к фактическому полной паре local/remote socket endpoints; серверные provider sockets не получают мобильные ограничения. Смена параметров не создаёт новых application sockets или нового logical session.

## Отказы и восстановление

5/10 обе половины, смена половин после полного восстановления предыдущей, 5→10 возврат аккаунтов. Сохраняются все application sockets/target dials, session/generation и exact bytes. Новые carrier epochs при возвращении ожидаемы. Самопроизвольный protocol-induced outage на здоровых аккаунтах — блокер, даже если supervisor быстро восстановил аккаунт.

Первая попытка после остановки ранее рабочего carrier начинается без дополнительного backoff. После отказа подключения применяется экспоненциальная задержка 1–16 s с jitter 0–50%; каждый аккаунт имеет независимую политику. Быстрое flapping не выдаёт новую немедленную попытку чаще раза в 10 s. Успешный TCP/IMAP dial без завершённого bootstrap не считается рабочим carrier. Квота, физические доказательства удаления и one-shot APPEND не ослабляются.

Перед вращением половин восстанавливаются ready carriers обоих endpoints всех аккаунтов. Lifetime monitor отслеживает остановки с создания стенда, включая прогрев. Исключение для намеренного outage привязано только к конкретным client/server carrier pointers; новый carrier того же аккаунта не наследует исключение. Ошибка немедленно попадает в измеритель и в итог fixture. Завершение всей fixture не считается outage.


## Нулевой допуск Go failures и regression veto

Последнее требование пользователя имеет приоритет над прежним допуском 5%: релиз запрещён, пока все обязательные Go tests и выбранные opt-in сценарии не пройдут. Численный люфт 10% остаётся только внутри заявленных performance boundaries. Нельзя удалять FAIL, пропускать упавшие legacy tests, смешивать failures с сотнями лёгких тестов или менять seed ради PASS. Незавершённые и не запущенные проверки не считаются PASS.

Матрица и число повторов фиксируются до финального запуска. Functional/proof/security/race/source/build failures, потеря приложения, protocol-induced outage и подтверждённая регрессия блокируют релиз.

Field4 и candidate выполняются одним стендом с одинаковыми профилями, seeds, потоками и длительностью. Overlay baseline содержит только новую test instrumentation и baseline NOOP/address API; транспортная логика field4 остаётся прежней, diff публикуется. Минимум три повтора на regression profiles. Сравниваются медианы per-direction mean/tail bandwidth и RTTp50/p95/max; deterioration>10%, выходящая за разброс повторов, блокирует релиз. Снижение bandwidth нельзя компенсировать повышенным RTT ceiling формулы. Исторические field4 числа также показаны, но не заменяют paired runs новых сетевых условий.

Все исходники trials, параметры, команды, возвратные коды и raw logs сохраняются. Публичный релиз требует exact-source checks одного ZIP и отдельного отчёта; Android/VPS/device/real-provider результаты не выводятся из Go-модели.

## Диагностика и проверка стенда

Для сети без потерь default probes сохраняют cadence/deadline1s. Для loss>0 default cadence/deadline3s относится к квалификации по новому hard cap3000ms; byte-clock всё равно независимый1s, окно скорости5s, max gap5s. Эти расписания фиксируются до прогонов и одинаковы у field4/candidate. Явный diagnostic cadence/deadline2–3s позволяет закончить измерение вместо обрыва на первой медленной echo; Для сети без потерь RTT gate и hard cap1000ms остаются прежними, поэтому такое превышение остаётся FAIL. Старые loss trials сохраняют свой старый FAIL; их нельзя переименовать в новый PASS. Probe сопоставляется с5s bandwidth window по Scheduled timestamp. Результаты разных cadence не сравниваются как paired data. Каждый steady-state interval проверяет здоровые carrier pointers/epochs на обеих сторонах; спонтанный rejoin не может скрыть protocol outage.

Performance calibration модели запускается отдельно безrace с `ITOM_NETWORK_CALIBRATION=1`, 10% для network ideal и объявленным50ms local copy/scheduler budget. Race не подтверждает скорость: он проверяет exact bytes, propagation, bounded deadline/cancellation; deterministic test отдельно запрещает byte-clock reset на late wake.

Complete performance FAIL не прекращает следующий recovery round; partial echo/corruption/transport failure остаются fatal. Исторические trials с отключением более 50% сохранены как старые результаты и не запускаются повторно.
