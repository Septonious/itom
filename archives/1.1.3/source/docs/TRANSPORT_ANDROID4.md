# android-4: upload, управляющие очереди и пакетная диагностика

## Наблюдения из присланных данных

Скриншот android-3: download 9.03 Мбит/с, upload 1.61 Мбит/с;
idle ping 528 мс, download-loaded 480 мс, upload-loaded 6428 мс, jitter 130 мс.
Это показывает асимметричную деградацию upload; результат не смешивался с
предыдущим замером 1.15/2.52 Мбит/с и 12201 мс под нагрузкой.

В серверном журнале использован только новый процесс PID 797918. Стартовые
SESSION_SUPERSEDED при замене подключения не принимались за новую неисправность.
Клиент: a06 receive / CONTROL_QUEUE_LIMIT в 18:46:40 UTC; сервер затем принимает
новую сессию этой линии. APPEND_UNKNOWN/CANCELED следом могут быть последствиями
отмены. Клиентские управляющие очереди доходили до 85/112, максимальное ожидание
на a06 — 5035 мс; сервер фиксировал очередь 174 и ожидание до 7997 мс.
Индивидуальные IMAP-операции в этих фрагментах обычно гораздо короче, чем ожидание
очереди. Рост RXAge после выключения клиента не считается активной неисправностью.

## Исправления

1. CleanupStatus ранее вызывал Wallet.Retirements() и повторно отправлял весь
   долговечный outbox для каждого подтверждения. N завершённых квот при задержке
   ответов создавали N(N+1)/2 сообщений вместо N. Теперь читается только запись
   соответствующей QuotaKey. Повтор для той же квоты ограничен интервалом 5 с;
   периодическая отправка и восстановление долговечного outbox сохранены.
   Удаление записи по-прежнему требует проверенного retirement ACK. Никакой
   преждевременной выдачи физической квоты или слепого повтора APPEND не добавлено.
2. Pump больше не делит остаток socket read пополам до 1 байта при нехватке
   stream/connection credit. AdmissionCapacity даёт точный минимум доступного
   окна, logical budget и MaxData. Один нечётный остаток окна становится одним
   кадром. При нулевом окне чтение удерживается до нового кредита, без busy loop.
3. Ранее внедрённые три IMAP-соединения, независимый GC, fair scheduling потоков,
   ограниченные окна и durable grants сохраняются. Wire v2 / ITH4 не менялись.

## Диагностический контракт

Трассировка включается автоматически при старте transport pool / server. Ошибка
открытия журнала выдаёт trace_unavailable, но не запрещает подключение VPN.
Сервер: `/var/lib/itom/tunnel-server/transport-trace.jsonl`, `.1`, `.2`.
Android: private noBackupFilesDir/transport/<profileId>/transport/, экспорт через UI.
Максимум три файла по 16 МиБ. Новый процесс имеет новый run ID; seq относится к
постановке события в очередь в пределах run, operation связывает начало/конец
операции. trace_drop/trace_stop — служебные записи без порядкового номера кадра.

- packet_tx_attempt / packet_rx: полный MIME-decoded транспортный body в base64,
  SHA-256, размер, UID/UIDVALIDITY где доступны, operation. Это попытка APPEND,
  а не утверждение доставки; её результат находится в imap_end с тем же operation.
- frame_queued / frame_sealed / frame_rx: тип, stream, logical, offset, counter
  где доступен, session. Управляющие поля WINDOW, RECEIPT, NACK, grants, retirement
  включаются; адрес CONNECT и папка UsageReport исключены. DATA plaintext исключён.
- data_writer_begin: метаданные кадра; data_grant_acquired: attempt с размером DATA
  и MIME, поток/смещение, wait; data_completion: attempt, outcome и код ошибки.
- control_wait: время от постановки до шифрования; imap_begin/end: длительность
  вызова адаптера в микросекундах. FETCH_PAGE включает внутренние SELECT/FETCH;
  сырые команды LOGIN/AUTH и TLS-поток не записываются.
- gc_candidate / gc_presence / gc_proven / gc_finished: проверяемые UID,
  подтверждённые ссылки и digest физических попыток; длительность и ошибка GC.
- lifecycle / health: состояния, реконнекты, сводка очередей/квот и состояния записи.
- Поля из отвергнутых сообщений не дают разрешения на доставку/GC. Неизвестные
  body без префикса ITOM записываются только как размер/hash. Наличие body в логе
  ещё не означает успешную аутентификацию; это подтверждается frame_rx.

Worker выполняет JSON/base64, запись, flush раз в 250 мс и ротацию. Producers
передают копии ciphertext/метаданных в очередь до 4 МиБ / 512 событий. Переполнение
явно учитывается в Dropped/trace_drop; дисковые ошибки — WriteErrors. Возможна
потеря хвоста при kill/power loss; это диагностика, не durable транспортный журнал.
Файлы 0600, новые каталоги 0700. Абсолютная полнота при неисправном/медленном диске
не обещается: диагностический I/O не должен останавливать VPN.

Пункт 10 менеджера — прежний journalctl -f, пункт 12 — tail -F полного JSONL,
пункт 13 — ZIP с трассировкой и capture.json. Android сохраняет обычный JSON и
дополнительный полный ZIP. UI получает только компактную сводку раз в секунду;
содержимое packet trace через JNI/state flow не передаётся. ZIP streaming на I/O
потоке, без загрузки 48 МиБ в память, с фиксированными именами и снимками размеров.
Открытые дескрипторы защищают от подмены файла ротацией после открытия. Экспорт
во время работы — best effort: возможны повтор поколения и незаконченный JSONL
хвост; анализатор должен дедуплицировать run/seq, исключая seq=0, и пропускать хвост.

Полный зашифрованный пакет включает открытые transport envelope metadata; это не
pcap и не захват каждого IP/TCP сегмента Android. Пароли, ключи и plaintext трафика
не выводятся. Аккаунты и пользовательские технические ID присутствуют в отчёте.

## Проверка и дальнейший замер

Регрессия: 32 квоты с задержанными retirement ACK + повтор всех CleanupStatus
дают ровно 32 отправки; истечение таймера одной квоты даёт одну дополнительную.
Нечётное окно 997 байт расходуется одной выдачей, connection credit и MaxData
соблюдаются. Трассировка проверена на ротацию, копирование буферов, конкурирующие
emit/Close, oversized overflow, исключение постороннего mail body. Серверный ZIP
не включает БД/профили и не перезаписывает существующий файл.

Новый стенд upload-only: реальный локальный TLS IMAP и TCP sink, одна линия,
80 мс на каждую IMAP-команду; отдельный echo-probe делит ту же линию с непрерывным
upload. Полная трассировка включена с обеих сторон. После probes проверяется
точное число принятых байтов и TCP half-close. Получено 983040 байт, idle 725 мс,
loaded p50 1010 мс / max 1821 мс, upload 0.807 Мбит/с. Это не сравнение скорости
Rambler с 10 аккаунтами и не обещание задержки на мобильной сети.

Все 18 core packages проходят go test -race, go vet без замечаний, native host
Go tests проходят. APK/AAR/NDK/Gradle/lint/Kotlin/device tests и серверные бинарники
здесь не собирались. Пользователь собирает локально и обновляет обе стороны.
Профили/UID/ключи/папки сохраняются, PURGE не нужен. После теста немедленно сохранить
оба полных ZIP: на высокой скорости 48 МиБ журнала могут покрывать короткий интервал.

Оставшиеся ограничения: один TCP flow закреплён за одним аккаунтом; TCP не
возобновляется при смене Noise-сессии; UDP кроме DNS, IPv6 и QUIC не туннелируются.
Реальные ограничения IMAP-соединений/частоты команд и производительность двух
пользователей на общем наборе аккаунтов требуют замера на провайдере.
