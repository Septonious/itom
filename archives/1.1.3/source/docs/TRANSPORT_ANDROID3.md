# Транспорт android-3: устранение задержек под нагрузкой

## Основание

Пользователь измерил 1844 ms без нагрузки, 12201 ms под нагрузкой и 1.15/2.52 Mbps.
В присланном серверном журнале 122 health-снимка: RTT p50 1398 ms, p95 4848 ms,
max 6601 ms; длительность последней IMAP-операции p50 97 ms, p95 251 ms.
В этом фрагменте нет событий reconnect. Эти снимки не являются распределением
всех IMAP-команд; по ним нельзя приписать провайдеру конкретную долю задержки.

В коде android-2 обнаружены последовательное выполнение чтения/GC в основном
обработчике сессии, один IMAP Client на все операции и общий mutex, удерживаемый
во время APPEND и всей очистки. TCP DATA обслуживались в порядке общих номеров
элементов, без чередования потоков. Каждый короткий socket Read мог создавать
отдельное письмо. UsageReport дополнительно отправлялся и адаптером, и Pump.

## Изменения

1. После handshake lane использует отдельные TLS IMAP-соединения для приёма,
   APPEND и GC. До появления аутентифицированного пользователя открыто одно.
   Все дополнительные Android-сокеты используют тот же protected dialer.
   При отказе дополнительного connect/login используются уже открытые соединения;
   число соединений и причина fallback явно записываются в диагностику. TLS не
   отключается. Для двух пользователей суммарно возможно до12 соединений/аккаунт:
   6 на VPS и по3 на двух клиентах. Возможности конкретного провайдера надо измерить.
2. Reader отдаёт ограниченные страницы отдельному обработчику. Один фоновый
   GC-worker получает снимки разрешённых удалений и возвращает подтверждённые
   результаты. Никакие сетевые вызовы больше не держат общий mutex lane.
   Обработчик продолжает принимать OPEN/PONG и ответы на TCP dial во время GC.
3. MAIL_RECEIPT, пришедший до окончания APPEND, сверяется при регистрации
   отправленного письма. Результат проверки наличия UID удаляет только counters
   из своего снимка; новые подтверждения не теряются. Очереди и outbox ограничены.
4. Для живого хвоста до16 UID чтение использует SELECT + UID FETCH без SEARCH.
   Для длинного/разреженного диапазона остаётся bounded SEARCH. Проверки размера,
   UIDVALIDITY, UID и тела сохраняются. После чтения полной страницы backlog
   вычитывается сразу, без ожидания очередного таймера основного обработчика.
5. OPEN/OPEN_OK/OPEN_ERROR/PING/PONG имеют приоритетную очередь. MAIL_RECEIPT
   сохраняет свой latest-only slot и отдельный резерв физической квоты, но может
   объединяться с обычным control в одном письме. Burst при заполнении urgent
   использует свободную обычную очередь. Очередь urgent64 + normal512, batch16.
6. DATA выбираются с чередованием TCP-потоков, с сохранением порядка элементов
   внутри каждого потока. Логический TX-буфер lane уменьшен с12 MiB до512 KiB,
   максимум512 items/1024 attempts; окно потока128 KiB. Большие неотправленные
   очереди не используются как способ увеличить скорость. Приём ограничен4 MiB.
7. Socket Read объединяются до32 KiB с фиксированным пределом ожидания2 ms.
   Маленький запрос не ждёт заполнения блока. EOF/half-close сохраняют последние
   уже прочитанные байты, даже если закрытый pipe отвергает изменение deadline.
8. До16 активных grants по64 KiB/1 message. Замена выдаётся после доказанного GC,
   без дополнительного ожидания обмена retirement. Retirement остаётся обязательным,
   всего не более64 записей с ещё не завершённым удалением метаданных. Физические
   пределы DATA8 MiB/128 сообщений и control2 MiB/128 сообщений не увеличены.
   UsageReport публикуется один раз, wallet по-прежнему обеспечивает повторную
   доставку при необходимости. APPEND с неизвестным результатом не повторяется.
9. В диагностику добавлены число IMAP-соединений, время ожидания control, время GC,
   число очищенных сообщений, APPEND count/bytes и FETCH messages. APPEND bytes —
   физические MIME-байты, не полезная скорость TCP. Секреты и адреса назначения
   не включаются в события.

Проверки точного тела/хеша, UIDVALIDITY и подтверждённого отсутствия при удалении
сохранены. Изменения не отменяют долги и не требуют PURGE, смены UID, ключей,
папок или переимпорта профиля. Handshake остаётся ITH4, wire — v2.
Обновить рекомендуется обе стороны: Android APK и сервер.

## Сравнение на стенде

Одинаковая модель: один аккаунт/пользователь, реальный TLS IMAP и TCP echo,
80 ms дополнительной задержки каждой SELECT/APPEND/SEARCH/FETCH/STORE/EXPUNGE.
Один bulk-поток непрерывно передаёт блоки32 KiB, пока второй выполняет8 коротких
прикладных echo-запросов. Затем bulk корректно закрывается, проверяются все байты.
Это application RTT, не ICMP ping и не внутренний PING, получивший приоритет.

| Метрика одного прогона | android-2 | android-3 |
|---|---:|---:|
| Первый прикладной RTT до bulk, ms | 2351 | 726 |
| RTT при непрерывной нагрузке, p50, ms | 6707 | 1418 |
| RTT при непрерывной нагрузке, max, ms | 9160 | 2430 |
| Полезная скорость upload+echo, Mbps | 0.319 | 1.524 |
| Передано и проверено в каждом направлении, bytes | 1146880 | 1343488 |

Объём различается: передача продолжается до завершения8 probes. Скорость — сумма
двух направлений за время передачи и завершающего drain. Это один сравнительный
прогон на локальном стенде, не обещание скорости/RTT на Rambler или Android.
Сырые результаты и границы проверки: `reports/android3-local/VALIDATION.md`.
Тест новой версии отклоняет p50>3 s или max>5 s на этом стенде.

## Оставшиеся ограничения

- Один TCP-поток закреплён за аккаунтом: striping одного потока по всем10 аккаунтам
  пока отсутствует. Разные потоки используют весь пул аккаунтов.
- UDP кроме DNS, QUIC и IPv6 не туннелируются. Автоматического обхода VPN через
  Direct нет. Бесшовного возобновления существующего TCP после reconnect нет.
- Скорость провайдера, лимиты соединений/команд, задержка появления письма у другого
  IMAP-соединения и поведение Android в фоне этим стендом не воспроизводятся.
- Fallback на меньшее число IMAP-соединений сохраняет работу, но ослабляет изоляцию
  APPEND/GC; следует проверить `event=io_mode` после обновления.
- Более крупные DATA-блоки, объединение DATA нескольких потоков в письмо, IDLE
  и объединение аккаунтов внутри одного TCP-потока здесь не объявлены реализованными.

Для следующего измерения достаточно обычного Speedtest/скачивания и экспорта
диагностики Android вместе с живым журналом за тот же интервал. Отдельный тестовый
релиз или очистка почты не нужны.

Нормативная основа операций UID: RFC9051 §§2.3.1.1, 6.3.2, 6.4.5,
https://www.rfc-editor.org/rfc/rfc9051.html .
