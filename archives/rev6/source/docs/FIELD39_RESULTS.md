# ITOM FIELD39 — результаты и границы проверки

Дата: 6 октября 2026. Ревизия `transport-s1-perf5-field18`.
Основа: точные исходники FIELD38/field17; источник SHA-256 `35f5d24dd19f916b502da9fedfd21724a4d119512af237eaf5da842fe47459c8`.

## Что показали обе полевые трассировки

Серверный архив содержит 78 009 событий, клиентский — 76 077. Оба относятся к FIELD38/field17, одному пользователю и десяти аккаунтам. Профиль нагрузки: множество коротких TCP-соединений — 217 OPEN, сотни FIN/STATUS/RESET и мало DATA. Скорость по этим архивам не квалифицируется.

В 17:52:17.816–17:52:17.832 UTC на клиенте почти одновременно завершились девять FETCH с `IO_OR_PROTOCOL_ERROR`, `reason=closed`, и один control APPEND с неопределённым исходом. Все десять carriers начали восстановление. Один повторный LOGIN получил `rejected`; это уже событие после первичного закрытия. В серверных логах позже появились CARRIER_REATTACH при новых аутентифицированных epochs — следствие восстановления клиента, а не доказательство первоначальной ошибки challenge.

`closed` объединяет EOF, reset и локальное закрытие; архив не позволяет доказать, что именно закрыло физические сокеты. Причина первого массового закрытия остаётся неустановленной. Проверка Android защиты/привязки сокетов по коду не замещает диагностику на устройстве.

Клиент отправил 141 RESET для нескольких потоков, получил только 8 RESET_ACK. Например, поток 69 обменялся TLS-данными и STATUS, затем многократно отправлял RESET без завершения. Это согласуется с выявленными дефектами завершения owner/маршрута, но сами цифры не доказывают единственную причину всей аварии.

В 17:54:21 клиентская трасса содержит `trace_stop`, экспорт показывает `OFF`. Сервер продолжал успешные IMAP-операции и через свой 25-секундный watchdog зарегистрировал потерю клиента. Поэтому второй серверный массовый таймаут не считается независимым подтверждением падения транспорта. Между часами сторон есть смещение; сопоставление выполнялось также по типам/потокам и метаданным пакетов.

## Изменения транспорта

- Ограниченная очередь непереданных STATUS/WINDOW/RECEIPT и терминальных ответов объединяет накопительные состояния одного потока. Уже попытанные/запечатанные записи, NACK и квотные descriptors не объединяются. Квотные подтверждения имеют отдельный приоритет.
- Таймаут DATA/FIN сбрасывает отдельный TCP-поток. Неотвечающий RESET становится тихим после конечного deadline; родственные потоки и carrier watchdog продолжают работать. Неподтверждённый физический долг сохраняется.
- Закрытие сокета больше не удаляет маршрут до authenticated RESET/ACK: позднее подтверждение доходит до Engine и освобождает согласованное логическое состояние.
- Полная очередь одного carrier позволяет отправить управление через другой живой carrier. Переполнение локального приёма после OPEN_OK отклоняет только новый сокет с RESET Final=0.
- Запоздалый probe уже подключённого клиента и challenge другого client nonce не запускают ложный reattach. Подлинный restart сервера и новый клиент по-прежнему обрабатываются.

Это локально проверенные исправления механизмов отказа, а не заявление, что первый физический обрыв в полевом архиве полностью устранён.

## Запрошенные изменения интерфейса

1. Android: видимый многострочный JSON, удалена галочка подтверждения; подсветка сохраняет символы, переносы и cursor offsets. Проверяются синтаксис, дубли ключей, глубина, схема/поля; показывается строка/столбец синтаксической ошибки. Добавлено форматирование. Текст при ошибке не удаляется.
2. Трассировка менеджера экспортируется прямо в `/tmp`, архив создаётся с правами 0600.
3. Выбор, удаление, изменение пароля и IMAP-проверка используют email; списки показывают email. Внутренние стабильные ID сохраняются для действующих журналов и authenticated bindings; переносить/сбрасывать журналы не нужно. Legacy ID alias сохранён для существующей автоматизации probe.
4. Ввод пароля в терминале видимый; ведущие/концевые пробелы сохраняются, снимается только перевод строки.
5. Интерактивный серверный экспорт выводит одну ссылку `itom://import#...`. Она содержит полный профиль и вставляется в Android импорт; «Проверить и форматировать» раскрывает JSON. Файловый API остаётся для прежних CLI-инструментов.

Rambler не отключён. Реальные провайдеры в лабораторном прогоне не использовались.

## HTTPS-модель: свежий FIELD38 против FIELD39

Один последовательный прогон каждой версии без параллельной сборки/race: реальный TCP/TLS/HTTP через production Go supervisors и локальный IMAP, доступ 130 Мбит/с, эмпирические задержки команд, старые 8MiB журналы, три потерянные startup публикации. Каждая фаза 30 секунд; tail — последние 10 секунд. Нет искусственного отключения более половины аккаунтов. Тест не использует Android TUN и настоящие Mail.ru/Rambler, поэтому результат не является полевой приёмкой.

| Фаза | FIELD38 Мбит/с | FIELD39 Мбит/с | FIELD39 tail Мбит/с | RTT max FIELD38 / FIELD39, мс |
|---|---:|---:|---:|---:|
| Download | 71,277 | 84,531 | 88,033 | 586 / 666 |
| Upload | 81,814 | 82,715 | 83,730 | 619 / 480 |
| Duplex download | 81,466 | 83,587 | 91,727 | 549 / 627 |
| Duplex upload | 76,939 | 79,629 | 82,394 | 549 / 627 |

FIELD38 в этом прогоне FAIL по download/tail 71,277/65,326; повтор для выбора удачного результата не выполнялся. FIELD39 PASS: каждая активная сторона и её tail >=75 Мбит/с, каждый HTTPS probe <1000 мс, неожиданных carrier exits 0, provider accepted=120/dropped=0. Допуск скорости 10% не снижает абсолютный floor 75. Скорость не ухудшилась; RTT upload улучшился, download/duplex вырос. Из одного прогона нельзя выводить статистически устойчивое преимущество или гарантировать результат на устройстве.

## Использование и следующий полевой шаг

Обновить сервер и APK одной ревизией. Сохранённые профили/журналы совместимы; удалять их для установки FIELD39 не требуется. Сначала проверить установление всех линий, затем открытие GitHub и инициализацию speedtest; при отказе экспортировать клиентскую и серверную трассы одного интервала до остановки соединения. Фиксировать отдельно действия пользователя, переключение Wi-Fi/mobile и момент отключения VPN.

Android compilation, Android lint, 57 Kotlin test cases и тесты устройства в этой среде не выполнялись. Их запускает Windows команда `all`; новый APK необходимо установить отдельно. FIELD39 подготовлен для полевой проверки, подтверждённой реальной приёмки >=75 Мбит/с пока нет.
