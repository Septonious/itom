# FIELD50: сеть 130 Мбит/с, RTT и параллельные TCP

## Исправленная исходная предпосылка

Пользователь 2026-10-08 уточнил: все показанные полевые speed-test результаты получены на стабильной сети **130 Мбит/с**, а не 20 Мбит/с. Последний скриншот: download 9.69, upload 8.03 Мбит/с, latency 574 мс, jitter 246 мс. Это примерно 7.45% и 6.18% от 130 Мбит/с. Замер idle около 500 мс и немедленный отказ обычного спидтеста остаются пользовательскими наблюдениями. Скриншот снят ещё во время upload; не превращать его в завершённую приёмку.

Критерий 5 Мбит/с / RTT <=1500 мс относится к отдельно заданной **сети 20 Мбит/с**. Его прохождение не объясняет и не оправдывает скорость на сети 130 Мбит/с. Нельзя считать низкую полевую скорость результатом радио или физического лимита 20 Мбит/с.

Старый localhost нагрузочный Go-тест проверяет целостность, bounded work и выживание владельцев. Его CPU-зависимый Mbps не прогнозирует Android/TUN, VPS, service delays публичной почты, маршрут до speed-test сервера и его протокол. HTTPS burst имеет 8 workers; отдельная постоянная короткая TCP проверка FIELD49 имеет только 3 подключения. Fixed-window тест начинает устойчивую нагрузку после OPEN/TLS и разминки; его 6 HTTP probes намеренно используют уже установленные соединения. Эти проверки нужны, но не воспроизводят начальный многопоточный запуск конкретного приложения.

## Что говорят сохранённые полевые traces

Разбор исходных клиентского и серверного архивов сохранён в `FIELD48_LIVE_ANALYSIS_2026-10-08.md`. Все 21 видимое OPEN TCP 8080 получили OPEN_OK. Выполнялись короткие обмены, после чего Android TCP copy завершался RESET/CLOSED; для FIELD48 нельзя определить read/write stage. Начало запуска вытеснено кольцом. Поэтому утверждать, что отказ вызван числом TCP, нельзя. Native лимит 128 workers и лимит 64 активных сокета на логического владельца действительно существуют, но данных об их достижении в момент отказа нет. Новые тесты не подменяют реальный Android прогон.

Распределение OPEN действительно имеет недостаток: рейтинг FIELD49 использует только `owner.active`, который повышается после OPEN_OK. Burst неотвеченных OPEN может направляться в заполненного быстрого владельца, несмотря на свободного соседа. FIELD50 резервирует ID и owner capacity под Client.mu ещё до отпускания выбора. Новый счётчик включает pending OPEN и активные routes. При 64 reservations выбирается другой здоровый owner; если все заполнены, только новый запрос получает ReasonCapacity. Пределы 64/socket-owner, 4096/session-ID, память, journal debt и криптография не увеличены. Retire, duplicate retire, carrier detach/rejoin и owner shutdown освобождают reservation ровно один раз. Замещение carrier не создаёт новый бюджет.

### Отмена открытия и поздний ответ

Дополнительно воспроизведён lifecycle bug FIELD49: caller отменяет OPEN после успешного server dial, но до доставки OPEN_OK. Client.open немедленно tombstone-ит route; dispatchStream отбрасывает поздний authenticated reply как frame закрытого stream. Server остаётся с одной занятой TCP allocation (client0/server1), без штатного FIN от клиента. Новый regression использует реальные supervisors, 25ms command delay и200ms visibility; runtime FIELD49 fails, FIELD50 PASS. Request, уже принятый actor, удерживает route/capacity до protocol completion или bounded OPEN timeout, чтобы позднее OPEN_OK закрыл непринятый app socket. Не принятое actor открытие освобождается сразу. OPEN_ERROR также terminal-ит route. На ошибке возвращается nil interface Stream. Это подтверждённый дефект, но факт его участия в отказе конкретного приложения в неполном trace не доказан.

## Ограничение глобального DATA окна

В первоначальной 130 Мбит/с модели useful duplex около 10.8 Мбит/с, а глобальный delivery window остаётся **1 МиБ**. Client ACK residence около 1005 мс, server около 965 мс при фиксированном target 800 мс. В реальном retained FIELD48 server health 41 nonempty-flight observations: окно всегда 1 МиБ, median residence 858 мс, max 1311 мс. На клиенте 27 observations: median window 1 МиБ, max 1.125 МиБ. Это не доказательство единственного bottleneck, но воспроизведённое ограничение.

Приближённый steady-state предел окна 1 МиБ и ACK cycle 0.8 с — 10.49 Мбит/с; это оценка, не отдельный benchmark. Delivery ACK включает mailbox-команды и обратную доставку контроля, поэтому абсолютная цель без оценки минимального DATA ACK пути может принимать неизбежное время подтверждения за очередь.

FIELD50 оценивает bounded lower-quartile ACK floor из восьми последних завершённых оригинальных bulk ranges, допущенных при общем flight <=512 КиБ; требуется четыре наблюдения. Repair инвалидирует floor sample перекрываемого original range. Full-window stall не повышает floor. Оценка ограничена 900 мс; target = max(800 мс, floor +300 мс), максимум 1200 мс. Окно увеличивается по 64 КиБ за decision epoch только при низком ACK residence и спросе, уменьшается при превышении target; диапазон 1–3 МиБ, fast reserve 128 КиБ неизменны. Адаптация не освобождает ни логические bytes без ACK, ни физический долг без доказательства удаления.

Это исправление контроллера требует проверки полезной скорости и прикладного RTT одновременно. Не увеличивать окно вручную только ради скорости и не объявлять изменение абсолютной цели улучшением idle RTT. Прикладная граница теста 20 Мбит/с остаётся <=1500 мс.

## Новые проверки и пределы доказательств

- Simultaneous TCP: 96 OPEN, затем 4 обмена на каждом, в том числе 32 КиБ, FIN и запрос после burst через production supervisors/TLS IMAP. Исходный FIELD49 проходит этот сценарий: простое увеличение числа до 96 само по себе не воспроизвело ошибку.
- Два регрессионных теста owner reservations падают с runtime FIELD49; FIELD50 проходит. Проверена локальность отказа при полном owner.
- Отдельный `model130`: calibrated 130 Мбит/с full-duplex, общий для всех клиентских IMAP sockets лимит каждого направления; **синтетический RTT доступа 250 мс** и явно предположенные provider service costs. Этот RTT не измерен на пользовательской сети. Default workload: 16 bulk streams каждого направления в duplex, 24 фоновых HTTPS workers, 6 warm probes, отдельные idle HTTP observations после 1.1 с паузы. Режим measurement-only, не приёмочный критерий 20 Мбит/с и не гарантия скорости 130.
- `model20` сохраняет точный прежний критерий каждого активного направления и хвостового окна >=5 Мбит/с, max RTT <=1500 мс, zero errors; результаты `model130` не могут завершить этот gate.

Числа всех выполненных измерений, исходные events, development attempts и перечень NOT_RUN находятся в `reports/field50/validation.json`. Причина отказа конкретного приложения и улучшение физического idle RTT остаются непроверенными. Следующий полевой export следует сделать сразу после первого отказа, чтобы старт не был вытеснен вторым долгим тестом.
