# ITOM FIELD40: аудит кода, изменений и замеров

Дата: 2026-10-07 (Europe/Moscow). База: `ITOM_TRANSPORT_FIELD39_FIX2_SOURCE.zip`, SHA256 `d8d5805ae3b041310c95d7dfe2adfa5878b865d3a813af4149450b3f750f608f`. Новая ревизия: `transport-s1-perf5-field19`.

## Вывод

Прежние зелёные Go-прогоны не подтверждали полевую работоспособность. Последний Windows failure обнаружил настоящий дефект готовности grants, а не просто слишком строгий тест. Аудит также нашёл независимо проверяемые ошибки управления ёмкостью, повторной публикации wallet, чтения через временный cleaner и обновления ключей. FIELD40 исправляет эти пути в production-коде.

Одновременное закрытие клиентских IMAP-сокетов в старой реальной трассе не имеет доказанной первопричины. Нельзя честно приписать его одному из найденных дефектов, Android, провайдеру или GC. Релиз не объявляет реальную скорость 75 Мбит/с и полевую стабильность подтверждёнными: для этого нужен новый прогон APK/VPS. Добавлены безопасные причины socket errors и Android network callbacks, чтобы следующий отказ оставил проверяемые данные.

## Материалы и охват

Инвентаризирован весь исходный архив FIX2:580 manifest entries, включая приложения, транспорт, сборочные инструменты, тесты, документацию, fixtures и vendored IMAP. Сопоставлены сохранённые архивы gate13, SOURCE26, FIELD35 и последняя рабочая база. История восстановлена из архивных снимков, отчётов и фактических пользовательских логов; отсутствующие git commits не реконструировались предположениями.

Это анализ всех частей проекта с подробным разбором критических путей, не заявление о формальной верификации каждой строки сторонней зависимости.

## Исправления production

### Grants: честная готовность и публикация метаданных

Клиент раньше объявлял READY после первого StorageGrant. Это мог быть только fast grant; bulk ещё не опубликован или задержан. Сервер также объявлял READY после quota-limited прохода offer, даже если обе пригодные service classes не выданы. Кроме того, ключ попадал в доступную writer очередь до установки его limit/class в map — конкурентный writer мог получить `GRANT_STATE` на корректном grant.

Теперь limit/class устанавливаются под mutex до публикации ключа. Первичная готовность требует наблюдения fast и bulk; у сервера — обеих выданных usable classes. После реальной активации временное исчерпание grants является backpressure, а не причиной отрыва аккаунта. Дубликаты не удваивают grant и не сбрасывают lifetime readiness.

### Переполнение служебной очереди и durable wallet

UsageReport и Release могут временно не попасть в заполненную очередь. Раньше эта ошибка доходила до завершения logical owner, хотя Spend/Fence уже сохранены и maintenance умеет их повторно публиковать.

Теперь только `CONTROL_QUEUE_LIMIT` для этих сохранённых публикаций откладывается. Quota не возвращается, fenced grant не переиспользуется, неизвестный APPEND не повторяется. Wallet Pending/Fenced остаются источником повторной доставки. Ошибки целостности, scope, отсутствующего grant и некорректных сумм не замаскированы. Неподтверждённый физический долг по-прежнему снимается только доказанной очисткой.

### Ёмкость TCP: локальный отказ вместо гибели owner

Client-side capacity handling был исправлен ранее, server OpenBook всё ещё возвращал fatal ErrCapacity при переполнении active sockets. Это могло завершить owner и его открытые потоки из-за очередного OPEN при веб-нагрузке.

Server registry теперь сохраняет tombstone непринятого ID и возвращает ReasonCapacity только для этого OPEN. Поздний duplicate не открывает новый target после освобождения места. Metadata exhaustion остаётся fail-closed. Если сервер уже dialled target, а pump admission возвращает credit/capacity pressure, сокет закрывается и возвращается per-stream отказ, без завершения owner.

### Исчерпание4096 stream IDs не сбрасывает активные TCP

Ранее после4096 монотонных stream IDs Client.rotateAttachment отменял все carriers и владельцев, включая ещё открытые TCP. Это самостоятельный долговременный путь к полному обрыву, хотя он не объясняет первый сбой после~217 OPEN в присланной трассе. Теперь при активных TCP отклоняется только новый OPEN с ReasonCapacity; logical tuple, owners и сокеты сохраняются. Полный rollover разрешён только в idle session. Allocation остановленного старого group запрещён. Ограниченная metadata4096 и запрет повторного использования IDs сохранены.

Материальное ограничение: после исчерпания этого session budget новые TCP не открываются, пока старые не закроются и не станет возможен idle rollover. Бесшовная неограниченная смена logical generations требует отдельного bounded routing/tombstone протокола; простое увеличение ID limit привело бы к неограниченному росту metadata. FIELD40 не скрывает это ограничение и не уничтожает активные потоки ради успешного нового OPEN.

### Отмена shared account runtime: устранён потерянный wake

У accountRuntime worker проверял отмену и засыпал под mutex, но Close и50мс cancellation timer уведомляли Cond без этого mutex. Отмена могла произойти между проверкой predicate и Wait; уведомление терялось, worker не завершался и Close ждал бесконечно. Это production lifetime race, а не основание увеличивать Go timeout. Контекст runtime теперь имеет cancellation callback с уведомлением под mutex; Close и admission timer используют тот же wakeWaiters. Состояние запроса, APPEND uncertainty и выдача debt не меняются. Существующий сценарий отмены выполнен100 раз после исправления; финальный gate проверяет также race.

### FETCH/IDLE и отказ временного cleaner

Опустевший mailbox при наличии глобальных активных TCP перестаёт опрашиваться каждые40мс. После двух пустых проходов используется IMAP IDLE с250мс audit; OPEN/PING/WINDOW сохраняют короткий hot path и DONE wake. Провайдер без IDLE сохраняет polling fallback. Cursor/gap/UIDVALIDITY проверки не отменены.

Длительный непрогрессирующий FETCH может использовать существующий cleaner как временный read-only fallback. Если cleaner закрывается maintenance repair, его ошибка раньше становилась reader failure всего carrier. Теперь исходный command сохраняет владение primary socket; streaming callback отключён; курсор не продвигается по неудавшемуся backup read. Дождаться завершения primary можно ограниченными200мс проходами; новые параллельные FETCH на тот же сокет не запускаются. Реальная ошибка primary, отмена lifetime или смена UIDVALIDITY остаётся ошибкой. Optional socket failure больше не является доказательством отказа primary.

### Смена физических ключей и повторный handshake

Soft key limit4GiB/1M records существовал в secure.Epoch, но transport его не использовал; длительная передача доходила до hard8GiB/2M records. Добавлена согласованная возможность rekey: решение о последовательности принимает только клиент. Сервер, достигший soft limit в download, запрашивает смену через аутентифицированный Echo token. Только один account lifetime планово меняется одновременно, смена начинается при сохранении хотя бы половины настроенного pool, lease снимается после готовности replacement и authenticated rejoin probe. Logical owner, TCP sockets, journaling и uncertainty сохраняются. Перед плановым close обе стороны прекращают новое DATA admission, завершают уже начатые APPEND и ждут authenticated MailReceived по старым outgoing counters. Server подтверждает drain; только после своего drain и peer acknowledgement клиент заменяет физическую сессию. Readiness новых grants не отменяет quiesce. Минимум половины рассчитывается по настроенному pool, включая ещё не активировавшиеся аккаунты, а не только по уже созданным owners.

При rejoin старый анонимный challenge из mailbox больше не принимается вместо ответа на свежий client nonce. Новый authenticated server challenge во время ожидания reply начинает новый раунд сразу. Handshake IDLE audit ограничен500мс; это короткая startup/recovery фаза, не постоянный500мс poll всех работающих линий.

Первоначальные новые проверки полного rekey за10/15с смешивали скорость durable inventory двух ОС с RTT приложения. В окончательном сценарии используется исходный bounded waitLane35с; продолжительность только записывается. Прежний неправильный25с watchdog всё равно отклоняется: exemption привязан к конкретному lifetime и точному CARRIER_REATTACH, а TRANSPORT_TIMEOUT остаётся unexpected failure. Параллельно тот же TCP должен продолжать обмен с2с deadline, owner не меняется и target не dialled повторно. Пользовательские hard75/RTT<1000 требования в HTTPS gate не изменены.

Промежуточная проверка обмена во время ротации выявила отмену APPEND с задержкой TCP. После добавления двустороннего drain принудительная ротация прошла за12.300с с обменом на том же TCP во время перехода; ещё три повтора прошли. Эти результаты относятся к локальному функциональному fixture.

Новая capability требует обновить одновременно APK и VPS. Старый field18 peer не считается совместимым с field19. Менять профиль, ключ пользователя или очищать state для обновления не требуется.

### Диагностика физического закрытия и Android сети

`ErrUnknown` сохранён через errors.Is; безопасная причина исходной ошибки APPEND больше не теряется. Reasons различают reset (включая Windows10054), EOF, socket_closed и IMAP BYE. Непроверенный provider error text в диагностический wrapper не сохраняется.

Android client trace записывает bounded события available/lost/capabilities/link_properties/selected/initial/session_stop и network_handle. Они позволяют сопоставить общий сетевой переход с массовым закрытием. Пароль, email profile, DNS IP и target payload в новые события не входят. Это диагностика, а не автоматическая гарантия восстановления любого отказа Android.

## Проверенные гипотезы, которые не стали исправлениями

- Гипотеза о постоянном4MiB лимите полного bulk FETCH опровергнута кодом: read budget расширяется по числу допустимых MIME сообщений. Нельзя увеличивать лимиты ради неверного объяснения.
- Timeout после пользовательской остановки не доказывает отказ до неё.
- Ошибки wsarecv/wsasend при закрытии упавшего fixture не считаются отдельными первопричинами.
- Старые RTT/model figures не подтверждают реальные Mail.ru/Rambler limits, серверные очереди и Android TUN path.
- IPv4 TCP/локальный HTTP2/TLS fixture не воспроизводит все условия мобильного устройства, QUIC/UDP/IPv6 и внешнего speedtest.
- Не выполнялись purge, сброс wallet/journal, возврат неопределённого APPEND debt или перенос долга в control reserve.

## Пользовательские изменения интерфейсов

Сохранены FIELD39: видимый импортируемый server IMAP профиль без trust checkbox, multiline editor с lint/позициями; серверный trace export в/tmp; выбор аккаунта по email вместо служебногоa01; видимый ввод пароля в терминале с сохранением пробелов; экспорт профиля одной `itom://import#...` ссылкой. Внутренние account IDs остаются в crypto/journal binding для совместимости сохранённого состояния, но не требуются для обычных manager действий.

## Стратегия проверки и пределы приёмки

Go — обязательный gate ошибок, race, compile и vet; не источник доверия к реальной скорости. Новые проверки входят в существующие сценарии, добавлен один объединённый admission/durable-pressure cohort. Массового добавления однотипных тестов нет. Количество PASS events включает subtests/fuzz seeds и не равно количеству независимых полевых сценариев.

Производственный путь дополнительно проверяется локальными TCP/TLS/HTTP2 и TLS/IMAP, integrity каждого app byte, cold start с прежними8MiB journals и потерянными публикациями3/10, ограниченными physical sessions, pending cleanup и малым трафиком под bulk. Модель130Мбит/с — ограничение клиентского доступа в каждом направлении; empirical latency только клиентская, VPS latency зеркалирована и не измерена отдельно. Нельзя называть такой fixture реальным провайдером.

Отключение более половины аккаунтов не является сценарием приёмки. Loss qualification отложена согласно последнему запросу. Скорость берётся отдельно по направлениям и устойчивому tail, с hard75; loaded application RTT берётся отдельно от IMAP Echo. Полезные bytes не суммируются для сокрытия слабого направления. Допуск10% применяется к заданным целям там, где он допустим, но не отменяет hard75 и актуальный строгий RTT<1000.

Полная Gradle Android assembly/lint/device и Windows execution здесь не заявляются. Реальный57-test domain JUnit и Go Windows cross-compile являются отдельными проверками, не заменой Android SDK/device или Windows запуску архива.

После успешного полного normal/race gate рабочий код не менялся. Последнее изменение только в сценарии rekey проверяется отдельно normal/race; повтор всех пакетов без изменения production не выполняется по последнему указанию пользователя.

Финальные фактические результаты и SHA256 архива находятся в отдельном `FIELD40_RESULTS.md` и приложенных логах. Неудачные промежуточные попытки тоже сохранены: они не считаются успешной приёмкой.
