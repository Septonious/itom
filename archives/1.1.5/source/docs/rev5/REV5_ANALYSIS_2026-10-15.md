# ITOM Rev5: field analysis and transport repairs

Rev5 addresses three distinct transport defects: a retained-quota reserve that prevented an otherwise live account from ever becoming ready, oversized receive pages on continuously paced downstream sockets, and downstream batching based on fast APPEND rather than peer BODY delivery. It also handles the separately reported provider mailbox-state setup error without creating folders or weakening UID proofs.

The supplied evidence establishes the quota deadlock and continuously slow Wi-Fi BODY transfer. The user subsequently confirmed the router issue: resetting it removed the earlier download bottleneck. The post-reset capture still contains application connection failures, while OpenSpeedTest completes. No account-ID/email mapping or fatal stack for the previously reported whole-app mobile crash is available. Those distinctions remain part of this release's qualification.

## 1. The dead account: six MiB of debt, twelve free ordinals, no grants

Every one of eight retained server health samples for a05 reports the same 6,571,914 charged DATA bytes and 180 charged messages, Stage=grants, zero available/issued grants, zero DATA attempts/appends/fetched messages. The server's persisted DATA profile is 12,582,912 bytes and 192 messages. The client simultaneously reports no usable grants. Control traffic remains live. A previous TRANSPORT_TIMEOUT remains in the server diagnostic field; it does not explain the stable held-ordinal boundary.

The recovery allocator reserved profile.Messages/16 = 12 message ordinals for local use. Exactly 12 were unused on this account. Recovery therefore refused every new remote grant even though real physical byte and message capacity remained. Old wallet history is missing on all fifteen accounts, including the other fourteen ready accounts; missing wallet history alone is not the discriminating failure.

The old retained-176 test reinforced this defect: it explicitly expected 179/180 retained messages to remain unready. Its assertion has been replaced with the actual boundary and preservation invariants, rather than deleted to conceal a failure.

Rev5 computes a stable reserve from historical charged exposure. It shares genuinely unused ordinals with remote fast and bulk grants while retaining at least two local ordinals for their local counterparts. The reserve does not shrink after each new grant. The exact 180/192 case leaves a six-ordinal local cushion and can issue both remote classes. The 188/192 boundary still permits the two remote classes plus two local ordinals; 189–192 correctly cannot fund all classes.

All physical limits, byte reserves and retained charges remain authoritative. Old-session grants are not usable as new-session DATA authority. Missing client history is never replaced by invented zero spend. Historical grants are paginated and charged using their recorded open limit or closed spend minus proven releases. No journal reset, wallet deletion, mailbox purge or quota forgiveness is part of the repair.

Tests recreate the exact field debt, check both local classes remain admissible, and compare the old grant before and after. A production-supervisor test uses fifteen real TLS/IMAP accounts with physical APPEND/EXPUNGE UID history, old reservations and absent client history. All thirty one-way echo directions must complete; a05 must then carry a 512 KiB duplex transfer and a short application exchange, with its historical charge unchanged.

The shaper still reproduces a transport robustness problem on a continuously paced socket; this fault must remain safe even when its external cause is corrected. ### Receive-page repair

The old reader fetched up to four complete bodies in one command. At the observed per-socket rate, four individually legal bodies could exceed the independent 30-second command cap despite constant progress. Reconnecting then repeats work on an otherwise live socket.

The new reader begins with one BODY. It expands to four only after a sufficiently large body demonstrates adequate transfer service. Empty polls and tiny control-like bodies cannot train that decision; a replacement connection starts cold. Callback backpressure is excluded from the service observation. The expansion threshold is size-normalized (4 Mbit/s, a 250 ms minimum budget and the independently calibrated unloaded NOOP propagation time), so healthy large pages do not lose batching merely because they take over 250 ms. Existing no-progress and absolute command bounds remain intact. UID cursors, incarnation checks and deletion proofs are unchanged.

A new test shaper operates below TLS, pacing each actual server-to-client TCP socket independently at 0.3 Mbit/s in 1,448-byte pieces, with upload unimpeded. A two-socket calibration checks both byte clocks within the approved 10% margin. Four actual 256 KiB payload messages reproduce the old 30-second failure after only three intact body callbacks. Rev5 drains all four in about 38 seconds over separate bounded commands, retains the same healthy socket, and keeps control NOOPs below 1,100 ms. A separate 40 Mbit/s TLS case requires 1,4,4 body pages: a healthy multi-body page taking over 250 ms must retain amortized FETCHes.

## 3. APPEND completion does not establish peer download service

A fast tagged APPEND only measures ingress to the provider. The old service policy could form large downstream envelopes while the peer's BODY socket was delivering at 0.3 Mbit/s. Application prefixes, repairs and short exchanges then waited behind whole envelopes. Extra blind connections or a shared low pool cap would not correctly distinguish an isolated slow account from a generally slow downstream path.

Rev5 starts cold or stale server-to-client bulk service with one complete 32 KiB DATA record. Only a complete authenticated MAIL_RECEIPT for a known successful physical bulk APPEND trains downstream batch size. Partial/duplicate acknowledgements cannot count twice; unknown APPEND outcomes and short or fast-class records cannot train it. A logical repair has distinct physical authenticated counters and can train its own completed physical copy. Two short successful turns double the target; two slow turns are needed to reduce a trained target, so one visibility outlier does not collapse it. Stale observations return to a conservative cold start. APPEND service remains a separate observation.

Full-suite HTTP testing then exposed an error in the initial receipt policy: the server's client-NOOP baseline is unset, so its service budget stayed at one second even on a healthy high-latency mobile path with four DATA shards. Receipts stayed cold at 32 KiB, consumed many of the few remaining physical message slots, and several 256 KiB concurrent GETs exceeded their existing 15-second deadlines. This reproduced independently, so the candidate was stopped despite its six passing isolated speed cases. Rev5 now uses the already authenticated **unloaded control-echo baseline** for the fixed propagation allowance. Current queue-inflated RTT cannot enlarge that allowance, and BODY receipts remain the only evidence for batch growth. A separate regression requires recovery on a two-second healthy receipt with an 800 ms unloaded baseline, while a 16-second BODY still shrinks the target even when the current loaded RTT is ten seconds. The receive-page classifier also accounts for the calibrated unloaded NOOP time: a healthy 32 KiB body on a 300 ms path must not be labelled slow merely for taking over 250 ms. A new actual-TLS mobile test requires 1,4,4 pages after that real NOOP calibration. Two short successful physical receipts, rather than four, now double the cold batch target so convergence does not consume most of the available message ordinals. HTTP deadlines and quota limits are unchanged.

The paced next-transfer test also caught a separate backlog defect after the propagation correction. Small envelopes could still accumulate behind a reader, so envelope size alone did not bound the next application's prefix. Rev5 bounds known, unread physical bulk bodies per carrier during cold/slow operation: one before the first observation or after sustained pacing, two during measured convergence, and the existing writer parallelism after the path is fully trained. Admission counts both an in-progress writer and successful physical copies awaiting complete receipts; completion signals waiting selectors. Fast DATA remains independently admitted. Unknown APPEND outcomes keep their original durable debt and do not create a permanent advisory scheduling block. New tests cover the cold bound, bounded convergence, completed-receipt wake-up, unknown outcomes and restored healthy parallelism. The same actual paced application case must still meet its original 3.3-second next-prefix deadline. The first complete repetition exposed a long-blackout deadlock: a wait for a pre-outage physical receipt could block fresh repair traffic after reattachment. The scheduling lease now expires after max(3 seconds, four unloaded control-echo RTTs), with its own timer to wake selection even without other traffic. Expiry does not erase counters, release quota, mark a physical message received, or retry an uncertain APPEND. A unit test exercises the timer without heartbeat/capacity signals and checks that old metadata remains intact. The original thirty-second blackout scenario must complete all eight in-flight 2 MiB exchanges on their original sockets, then serve a new request. The concurrent journal-capacity unit explicitly establishes a trained healthy path before checking the unchanged ten-reservation quota boundary; separate Rev5 tests check cold/slow admission.

This feedback changes advisory envelope size only. It does not alter logical delivery receipts, application RTT, flow/window authority, durable accounting, physical cleanup proof, or the wire protocol version. Quiet reserved interactive readers are excluded from the bulk-service median; one slow bulk account cannot shrink the healthy bulk pool.

New tests cover partial/full/duplicate/unknown/short receipts, isolated outliers, sustained paced service, healthy recovery, pool isolation and RTT isolation. The actual TLS application case runs four simultaneous paced download streams plus short exchanges; after the initial transfer it requires the next 32 KiB application prefix within 3.3 seconds and the intact remainder within its independent deadline, while retaining reader sockets and avoiding carrier exits. Nominal 100 Mbit/s qualification is a separate unpaced-provider scenario; a 0.3 Mbit/s physical-path test cannot honestly require 90 Mbit/s.

## 4. Recovery must restore DATA workers as well as control carriers

Three complete field-suite repetitions passed, but the fourth run with 12 ms added durable-commit delay failed the existing thirty-second blackout scenario: seven original 2 MiB TCP exchanges missed their unchanged sixty-second deadline. A separate traced reproduction also failed. The earlier advisory receipt lease fixed one recovery wait but did not resolve this failure, so those passes were insufficient for release.

Runtime snapshots exposed ready, authenticated carrier replacements with no available shared DATA workers. In one snapshot reproduction, two accounts remained unavailable throughout the rest of a run while the other two carried every new bulk publication. In the failing trace, three accounts published almost no new DATA for roughly fifteen seconds after becoming ready. The shared account dial gate and the DATA worker each maintained independent exponential sleeps up to thirty seconds. Thus a working control replacement did not promptly restore its DATA service.

Rev5 now applies the existing ninety-second logical-session survival interval to the shared account gate and both shared/client DATA repair waits. For a previously authenticated account, each retry delay is capped at two seconds during that interval, with existing subtractive jitter and serialized account dial admission retained. Cold accounts and outages exceeding the survival interval retain exponential pacing up to thirty seconds. No uncertain APPEND is replayed, no queued payload is discarded, and no durable charge is released by this scheduling change. The original blackout test passed twice with the twelve-millisecond commit delay after this repair; the complete frozen candidate still requires every gate afresh. A separate regression verifies authenticated versus cold/prolonged pacing without weakening cancellation or permanent-error classification.

## 5. Router reset separates app failures from a whole-tunnel outage

The added capture identifies itself as **0.9.2-Rev4-debug**. It retains UTC 12:15:22.400–12:17:22.622 (Moscow 15:15–15:17), starts after the session has already produced about 67,000 trace records, and has no simultaneous server capture. The user ran two or three regular Speedtest-app tests that ended with an error when ramping above 20–30 Mbit/s, then successfully ran the OpenSpeedTest website shown in the screenshot (35.8 Mbit/s down, 28.1 Mbit/s up, 312 ms ping). These are user-reported application identities; the transport trace has no site labels or plaintext traffic.

The retained client trace contains 20,149 successful IMAP operations, 919 successful DATA APPENDs, and no recorded lane loss before the final stop. Nine canceled IMAP operations and one uncertain control APPEND occur at stop. Repeated network-capability callbacks keep the same underlying-network handle. Account a05 remains in the same grant-wait state, independent of the router correction.

Nineteen target OPEN results report code 7 (`ReasonNetwork`): eleven at UTC 12:15:34.715–38.140 and eight at 12:16:15.905–18.165. In this IPv4 TCP exit implementation, a failed DNS lookup is the ordinary path producing that code; connection refusal and timeout have other codes. The server's per-target DNS/connect diagnostic is absent for this session, so the precise resolver failure and its relationship to the app's ramp error remain unconfirmed. These failures must not be called IMAP lane crashes. Rev5 records fixed target-DNS reasons (`not_found`, `temporary`, `timeout`, `canceled`, `failed`) without retaining resolver names, addresses or error text. A regression verifies each failed target releases its dial slot and the next numeric target can still connect. There is no speculative public-resolver fallback or retry of permanent DNS failure.

The trace also has eight application-side read resets, each followed by closure of that stream's opposite direction. Two later socket-write closures follow the earlier local application resets. These do not establish a carrier failure. Download stream 405 completes 71,703,349 bytes with normal EOF; upload stream 431 completes 51,139,998 bytes with normal EOF and then receives its response. At 12:17:00, stream 431 has 3,342,336 logical bytes queued behind acknowledgements; by 12:17:09 its upload copy completes and by 12:17:10 its response completes. A single queued snapshot is not proof of a permanent transport stall. The trace cannot prove which unlabeled stream belongs to every failed app test, and successful OpenSpeedTest is not proof that the regular app regression is fixed.

A new production-supervisor application regression uses fifteen real TLS/IMAP accounts, retained journals and physical UID history, a 240 ms mobile path and 40 Mbit/s socket pacing. It performs three consecutive 1→4→12 connection ramps. Half the downloads close after a verified 128 KiB prefix; the others verify all 512 KiB. An original chat socket must exchange verified payloads within 1.1 seconds during every phase. A final intact download and another exchange on the original chat must succeed after all aborted ramps. This checks fanout, cancellation cleanup and subsequent usability in addition to sustained synthetic throughput. It does not impersonate the proprietary Speedtest app or claim direct field qualification.

## 6. Provider mailbox-state rejection is a bounded setup retry

The separately pasted `NO [SERVERBUG] Mailbox uidvalidity changed` reply is a provider selection/setup failure. It is not proven to belong to a05: the exports contain no ID-to-email mapping.

Previously, any unsuccessful SELECT during folder setup could lead to CREATE. Rev5 recognizes this specific typed NO/SERVERBUG reply as IMAP_MAILBOX_STATE_CHANGED, exports a fixed safe reason, and allows folder checking one retry on a fresh connection (two attempts total, 45-second outer bound). CREATE is restricted to explicit missing-folder responses. No APPEND is retried by this helper. A stored locator's actual UIDVALIDITY mismatch remains a different, nonretryable proof error; it cannot authorize deletion or release of quota.

Actual TLS tests inject one transient rejection and persistent rejections. They require respectively recovery or a bounded stop, exactly two fresh connections, zero CREATE commands, and sanitized diagnostics. The manager now prints the account ID beside the username so future field failures can be mapped without guessing. Account diagnostics also expose DATA profile limits, the batch target and a bounded grant-wait reason.

## 7. Global and individual server messages

Manager menu 17 now shows the global message and provides global edit/clear plus selection of an individual client by UID. An individual message overrides the global text for that client only. Removing an individual override restores the global message. Saving or clearing a global message atomically deletes every individual entry, including when the saved global text is unchanged. Settings persist in server.db; active sessions receive updates through the existing authenticated notice/acknowledgement path without restarting transport. One monotonic configuration revision prevents an override removal from rolling a client back to an already superseded global revision. Removing a client also removes its message entry.

The equivalent commands are `itom message --text "&eGlobal message"`, `itom message --uid CLIENT_UID --text "&cIndividual message"`, and `itom message --uid CLIENT_UID --clear`. Omitting UID addresses the global message. The message body remains limited to 2,048 UTF-8 bytes. Configurations with individual messages use schema 5; Rev5 still reads earlier supported schemas.

The Android home-screen message card renders legacy Minecraft-style colors `&0`–`&f` case-insensitively, with `&l` bold, `&o` italic, `&n` underline, `&m` strikethrough and `&r` reset. A color code resets prior style flags; `&&` emits a literal ampersand. Unknown codes stay readable. Thus `&cHello &aWorld` displays red “Hello” and green “World”. Color and style parsing are presentation only; authenticated message text and revision semantics are unchanged. Domain tests cover all sixteen colors, Unicode, escapes, styles and resets; Android adapter tests verify actual rendered color spans and return to the theme color. Persistent configuration, CLI/menu targeting and two-client TLS delivery tests cover override isolation, removal, global replacement and global clearing.

Its fixed 250 ms receive-page classifier was corrected to use bytes transferred, and the fast-large-page regression above was added. Another run recorded only 29/30 full-duplex probe-overlap observations: the zero-phase first probe had only its short echo interval to observe bulk progress, whereas later probes had the preceding two seconds. This is retained as failed evidence, with the confound disclosed; it is not silently accepted. The complete six-run matrix is repeated with log analysis, compression and other builds paused. ## 10. Repeated chat traffic and split-reader affinity

A later full candidate failed the ramp/abort chat check even though several focused repetitions had passed. It was retained as a failure. Two scheduling defects were isolated: small exchanges accumulated toward the fragmented-bulk threshold indefinitely while the socket never had a two-second idle gap, and split-mailbox short-response placement charged unrelated bulk-reader occupancy despite an independent fast mailbox and slot. Deterministic regressions failed before the fixes. Fragment volume now uses bounded two-second windows while sustained small-packet bulk retains its class; split short placement excludes bulk cost only when that independent topology exists. Mixed-mailbox accounting and actual urgent/control pressure remain authoritative. Six focused ramp repetitions then passed, with the maximum chat RTT about 771 ms.

## 11. Cleanup proof reuse removes avoidable throughput overhead

The next transport checkpoint passed both 32-case field suites and all three MULTI runs, but all three SINGLE runs failed the sustained download criterion. Their lowest useful rates were about 85.87–89.11 Mbit/s, while every loaded latency probe passed. These failures were not averaged away or accepted as within the existing 10% margin.

A separate diagnostic SINGLE profile recorded 118.73 CPU seconds over 84.03 wall seconds on the two-core host. Cleanup accounted for about 25.54 CPU seconds, and MIME decoding for about 22.08 CPU seconds; the allocation profile recorded 70.50 GB of cumulative allocation. The same owned immutable MIME rows were repeatedly Base64-decoded and hashed during retention filtering, candidate matching, canonical-charge calculation and cleanup. This was unnecessary work even when the physical proof was unchanged within one sweep.

Rev5 now parses each owned physical representation once per cleanup invocation. Its decoded body, canonical charge and digest can be reused within that invocation. The cache is keyed to that exact immutable buffer and length; it is discarded and its decoded bodies cleared when the sweep ends. It is never carried across FETCH, reconnect, UIDVALIDITY changes or a later sweep. Each attempt still undergoes its independent folder, account, batch, UID, journal observation, deletion and absence checks. Distinct identical physical copies still cannot prove multiple attempts from one UID. Provider-rewritten and invalid physical representations retain the existing conservative proof rules.

The subsequent fresh checkpoint passed all six speed cases. The minimum verified useful rates were approximately 96.99, 95.45 and 96.22 Mbit/s for SINGLE, and 101.20, 99.92 and 99.59 Mbit/s for MULTI; maximum loaded RTT remained below 550 ms. Both the normal and 12 ms delayed-commit 32-case field suites also passed. These checkpoint measurements describe that source, not a waiver for later edits: the final combined app/server source must pass the complete release pipeline again.

## 12. Android UI and authenticated server administration

The Android theme now uses darker neutral surfaces, brighter text, stronger control boundaries and vivid cyan, green and violet accents. Android contrast tests cover body/action text and input boundaries. Existing system font scaling, scrolling and touch behavior remain active. Initial feature builds passed 81 domain tests, seven app tests and lint with zero errors or warnings; the final source is rebuilt and tested independently for release.

The new Settings admin tab follows the enabled server-side client named `admin`. Commands use a typed, bounded protocol on the existing encrypted IMAP stream. The server rechecks the current UID/key and role for each command. A fresh per-connection HMAC challenge additionally distinguishes trusted app management from unrelated applications routed through the same admin VPN. Status responses exclude passwords and keys. There is no public administration listener or arbitrary shell command.

Reversible configuration/service actions are protected by a durable transaction and an independent systemd watchdog armed before application. Loss of verified two-way recovery for sixty seconds starts rollback; sixty continuous healthy seconds commits the change. Heartbeats continue independently of the visible tab and reconnect using the same pending transaction. One-use echoes cannot extend a trial through replay or a dead downlink. The guard blocks conflicting CLI configuration writes and rejects stale app forms. Rollback preserves notice monotonicity, newly published identity fences and every physical journal. Service reinstall recovery also restores the original unit and boot-enablement link. Watchdog restart and server boot resume pending recovery. Irreversible purge, uninstall and journal migration remain CLI-only, as requested.

The app provides clients, accounts, invitations, global/individual formatted messages, service controls, resource settings, live traffic/logs/trace and chunked diagnostic export. Its online account check selects existing mailboxes and exercises the provider UIDVALIDITY failure path without creating missing folders. The complete control mapping and trial behavior are documented in [ADMIN.md](ADMIN.md).

The final release pipeline has ten required gates: Python checks, Android build/tests/lint, three complete field-suite repetitions, the delayed-commit suite, complete core/server qualification, accounting/admin race tests, recovery race tests, native vet, the native admin IMAP/reconnect race test, and the six isolated SINGLE/MULTI speed cases. Every gate must pass on one frozen source identity. Actual systemd hosting, live Rambler service and a physical Android device remain outside the workspace validation scope.

The native admin regression also leaves the phone-side logical pool running while replacing the real server supervisor and management service, using the same durable journals and trial database. The focused race run recovered its verified heartbeat after this server restart in 10,069 ms. This is distinct from a client restart and directly exercises the connection path used by service-control actions; it still does not substitute for testing a real systemd host.
