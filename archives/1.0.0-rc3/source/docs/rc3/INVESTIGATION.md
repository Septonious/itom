# RC3 latency adjustment

The user reports sustained high speeds and no failed Speedtest runs on RC2. Screenshots show roughly 83–98 Mbps download, 61–123 Mbps upload, 329–369 ms idle RTT, and 54–252 ms jitter. These are user field results, not new RC3 measurements. The latest paired traces identify RC2 and cover roughly 00:28:39–00:30:24 UTC on 17 October 2026 (server tail extends to 00:30:33).

209 complete control echo pairs have minimum 216.21 ms, median 345.83 ms, p95 619.57 ms, maximum 892.21 ms. Local PING queue median is 1.59 ms (p95 66.97); server reply turnaround median is 11.01 ms. Median physical control APPEND duration is 53.9 ms client and 65.5 ms server; median control FETCH is 17.0/27.4 ms. Most delay is in the complete provider path, not a large constant local queue. Cross-host components depend on clock agreement; client round trips and each local operation duration do not. IMAP echo RTT and Speedtest RTT/jitter are distinct measurements.

A concrete avoidable component is the hot empty-reader sleep: 10,20,40,80,80... ms, while waiting for a latency-sensitive response. RC3 changes only this bounded search to 10,20,20,20... ms. This removes up to 60 ms of artificial wait per reader turn (up to 120 ms across two independently unlucky request/reply waits), without changing command RTT or claiming that worst-case saving applies to every exchange. Actual visible UID backlog continues draining immediately. Ordinary active 20/40/80 ms and quiet 250/500/1000/1500/2000 ms backoff remain unchanged. The existing response-hint/parallel-short-demand windows still bound the higher polling rate; there are no additional sockets, LOGINs, background workers or wire messages. Commands remain serialized and receive progress/cursor proof rules are unchanged.

The existing forty/ eighty millisecond hot sleeps are reproduced by a before-fix test which rejects a delay over twenty milliseconds. After the change, focused race checks verify bounded nonzero polling, immediate backlog draining, quiet fallback, existing reader ownership/repair and the earlier RC2/V1 routing/repair invariants. Normal full-supervisor recovery checks retain the twelve concurrent TCP streams, temporary provider pause, persistent blackhole, correlated physical EOF and original/fresh post-load connections. This finite integrity/recovery workload is not a sustained 100 Mbps or sub-200 ms certificate.

Higher command frequency during a bounded response search is the tradeoff. Field confirmation is still required to establish its effect on throughput and latency on the real provider. No global flight, batching, bulk writer, quota, LOGIN or congestion limits were changed. No physical journal debt is released by a timer. Already working persistent connections, account-stall routing, early authenticated NACK retention and bounded receive-blackhole repair are preserved.

Sub-200 ms is an optimization target, not a measured result: even the minimum RC2 echo in this retained sample is 216 ms. The provider/network path may need improvement to achieve it consistently. No speedtest RTT display or metric is modified to create an apparent gain. The historical RC2 instrumented startup-discovery timeout remains unresolved; the user's successful real-provider runs do not prove its cause fixed. RC3 remains a testing prerelease, with full internal/live qualification outstanding. Raw user captures and credentials are private.
