# FIELD35 — исправления по полевым логам

## Исходные наблюдения

Локальный ITOM_dll.zip, только последний run 1791217675382197528: 2026-10-05 16:27:55–16:30:06 UTC, 76424 записи. Активны a01,a03,a05,a07,a09,a10,a11; a02,a06,a08 остаются на grants без reconnect. Получено 20 WRITE_GRANT, из них только одно bulk-разрешение 2 MiB/32; для трёх зависших аккаунтов WRITE_GRANT не наблюдалось. Из 640 DATA APPEND 637 fast и 3 bulk, около 488 KB upload. APPEND DATA медиана 61,5 мс, p95 140,3 мс; FETCH медиана 15,6 мс, p95 54,3 мс, максимум успешного FETCH 14,903 с. Нулевые показатели после выключения VPN исключены из анализа.

Есть только клиентские логи. Утрата публикации старого grant воспроизведена как достаточная причина аналогичного зависания, но не доказана как единственная причина данного полевого сбоя. Долг настоящего server journal неизвестен.

## Исправления и доказательства

Основные воспроизведённые причины покрыты компактными регрессионными проверками:

- три старых журнала с неполученными публикациями grant блокируют READY; восстановление через согласованную возможность GRANT_RECONCILE и собственную историю wallet;
- отсутствие раннего ACK регистрации descriptor оставляет лишнюю очередь Pending; Registered подтверждается отдельно от Released без возврата квоты;
- активный пустой reader отправляет 56 FETCH за 1,2 с; ограниченное 10/20/40 ms ожидание, явное пробуждение;
- STATUS обгоняет ещё не завершённый DATA APPEND; исключены параллельный repair и ранний NACK в течение 500 ms после commit;
- bulk заполняет все BODY reader; два аккаунта в пуле от пяти пригодных оставляются для коротких DATA;
- три больших BODY исчерпывают byte grant до порога 16 сообщений; byte pressure запускает очистку раньше;
- исчерпанный wallet grant удерживает worker на одном аккаунте; подтверждённый rollback до APPEND возвращает работу общему пулу, прежний неизвестный долг сохраняется;
- bulk-only аккаунт ошибочно считался fast spare; резерв очистки теперь учитывает только реально пригодные fast-разрешения.

Дополнительные исправления при завершении:

- подтверждённо не отправленный APPEND не тратит бюджет трёх физических попыток; неизвестные результаты остаются ограничены прежним бюджетом;
- максимум пять одновременно допущенных bulk APPEND, включая bypass governor; очередь не разрастается до двадцати крупных BODY до поступления RTT feedback;
- очистка двух выделенных reader выполняется по очереди; debt-bound recovery сохраняет возможность прогресса;
- если FETCH перестал получать TCP байты на200 ms для двух выделенных reader или350 ms для bulk, чтение переходит на существующий изолированный cleaner, без новых соединений и повторной отправки DATA. Большой BODY с поступающими байтами не дублируется. Original command drain присоединён к Close barrier;
- bounded TailDiscovery переносит пропущенные UID между сокетами, сохраняет исходные TTL и не даёт права возврата квоты. SELECT учитывает фактически выбранную папку резервного соединения;
- поздние streaming callbacks исходного FETCH блокируются до начала резервного; после успешного tagged completion основной reader возвращается в работу;
- новые диагностики показывают число read handoff.

Финальные результаты и точное состояние Go/race/build приведены в FIELD35_TEST_RESULTS.json и отдельном отчёте ITOM_FIELD35_RESULTS.md. Порог RTT не ослаблялся. Восстановленный вариант с watchdog350 ms отклонён: при задержках FETCH один HTTPS probe вышел за1 s. Сокращённое ожидание на двух выделенных reader оставляет время для обоих направлений запроса; bulk использует350 ms, чтобы не мешать очистке частыми резервными чтениями. Для коротких DATA выделенные reader получают конечное преимущество в score512, с сохранением fallback на общий пул.

## Новая нагрузочная модель

Настоящие TLS IMAP соединения production supervisor и HTTPS/1.1, проверка всех принятых приложением байтов. Сохранённые 8-MiB журналы и три потерянных grant publication; не свежий уже прогретый raw Echo. 130 Мбит/с ограничивает суммарный клиентский доступ в каждом направлении. Дополнительный RTT не добавляется поверх наблюдаемых задержек команд. Распределения client-operation latency зеркалируются на server side, потому что отдельных server logs нет; это приближение, не эмуляция rate limit или коррелированной нагрузки провайдера.

Все 12 успешных FETCH >500 ms сохранены в исходной фикстуре. Они вынесены в отдельный явно включаемый сценарий: по одному FETCH на a02,a06,a08 после 20 s задерживается на худшие 14,903 s, без отключения аккаунтов. Обычный режим не доказывает устойчивость к этому хвосту.

Измеряются cold HTTPS requests, download/upload/duplex по 30 s и последние 10 s отдельно. Clock включает запуск bulk/TLS. Одновременно каждую секунду идёт HTTPS ping с жёстким deadline 1 s. Порог75 Мбит/с не снижается допуском10%. Скорость порядка100+ на raw130 невозможна при текущем MIME/base64: грубый потолок130×3/4×76/78=95 Мбит/с до остальных расходов.

Все неудачные предыдущие прогоны сохранены. Один прогон upload-check содержит ложное отнесение отменённого HTTP handler предыдущей фазы к следующей; этот дефект измерителя исправлен, такой сбой не считается доказательством ошибки транспорта.

## Область проверки

Стенд подтверждает только указанную модель. Реальная успешная сборка Android/APK, lint/device tests и speedtest через настоящего почтового провайдера должны подтверждаться отдельно. Сырые журналы неудачных вариантов сохранены в наборе результатов; отменённый прогон не считается ни PASS, ни завершённым испытанием.
